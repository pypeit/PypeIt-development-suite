# Breaking-change assessment: merging `develop` into `release` (v2.1.0)

**Date:** 2026-11-02
**Compared:** `origin/release` @ `826bad5ce` (v2.0.x) vs. `develop` @ `b28dffd64`
(`release` is a direct ancestor of `develop`; the merge is a fast-forward of 631 files,
+74k/−20k lines.)

**Definition used** (from `doc/installing.rst`, "Versioning"): a change is *breaking* if it is
backwards-incompatible in a user-facing component: (1) the format of input configuration
files (`*.pypeit`, `*.coadd1d`, `*.coadd3d`, etc.), (2) user-level parameter names, or (3) the
format/datamodel of the primary output products. Internal code reorganization is not breaking.

## Bottom line

**The claim of "no breaking changes" in `doc/releases/2.1.0dev.rst` is not correct.**
There are **four confirmed breaking changes**:

1. Release-era `spec2d_*.fits` files cannot be read by `develop`.
2. Release-era `Slits_*` calibration files cannot be read by `develop`.
3. Release-era `Flat_*` calibration files cannot be read by `develop`.
4. The `[reduce] [[cube]] align` parameter was removed (replaced by `alignment_method`).
   Input files that set it, including the examples in the release docs, now fault.

In all of (1)–(3) the files fail to load **even with `chk_version=False`**. As things stand,
this means either (a) the release should be tagged **3.0.0**, or (b) small
backwards-compatibility shims should be added before tagging 2.1.0 (see
[Recommendations](#recommendations)). A few further changes alter user-facing behavior or
file names without being strict format breaks; these should at least be listed in the release
notes.

## How this was assessed

To avoid relying only on reading the diff, the two branches were compared mechanically:

* A `git worktree` of `origin/release` was imported side by side with `develop`. Both
  imported every `pypeit` module (excluding GUI/tests) cleanly. A script dumped the
  following from each branch for comparison:
  * every `DataContainer` subclass: `version` and `datamodel` (keys, `otype`, `atype`);
  * every `ParSet` in `pypeitpar.py`: keys, defaults, dtypes, options;
  * every spectrograph: `pypeline`, `configuration_keys()`, `pypeit_file_keys()`, `meta`
    keys, `ndet`, and the full `default_pypeit_par()` configuration;
  * every console-script entry point in `pyproject.toml`: all `argparse` options.
* **Round-trip I/O tests:** output products were written with the *release* code and read
  back with the *develop* code (`SlitTraceSet`, `AllSpec2DObj`, `FlatImages`, `SpecObjs`,
  `DataCube`).
* Diffs were read by hand for `inputfiles.py`, `metadata.py`, `pypeit_steps.py`,
  `outputfiles.py`, `specobjs.py`, `specobj.py`, `spec2dobj.py`, `manual_extract.py`,
  `collate.py`, `core/datacube.py`, `pyproject.toml`, and the `pypeit/data` tree.

The scripts are in the session scratchpad (`dump_dm.py`, `dump_scripts.py`,
`dump_specpar.py`, `rt_write.py`) and can be rerun if needed.

## 1. Confirmed breaking changes

### 1.1 `SlitTraceSet` datamodel: `pad` changed from `int` to a 2-element float array

* `pypeit/slittrace.py`: `version` `1.1.5` → `1.1.6`; `pad` changed from `otype=int` to
  `otype=np.ndarray, atype=float`. This supports asymmetric padding of the pinhole/standard
  star edge-tracing feature.
* **Round-trip result** (release-written Slits file, read by develop):
  * `chk_version=True` → `PypeItDataModelError: Current version of SlitTraceSet object in
    code (1.1.6) does not match version used to write your HDU(s)!`
  * `chk_version=False` → `TypeError: Cannot assign object of type <class 'int'> to pad.
    Allowed type(s) are: <class 'numpy.ndarray'>`
* **User impact:**
  * Existing `Calibrations/Slits_*.fits.gz` files cannot be reused.
    `Calibrations.get_slits` → `process_load_selection` loads the Slits file, and the
    reduction crashes instead of rebuilding. Users must delete their `Calibrations/`
    directory (or at least the Slits files) before re-running. This also affects
    `pypeit_ql` with existing calibrations and `pypeit_chk_edges`/`pypeit_chk_flats`.
  * See 1.2: this also breaks every existing spec2d file.

### 1.2 `spec2d` files: unreadable because of the nested `SlitTraceSet`

* `Spec2DObj` (still `1.1.1`) nests `slits: SlitTraceSet`. The nested version mismatch
  propagates up through `DataContainer._parse` (`datamodel.py:1028`).
* **Round-trip result** (release-written `spec2d`, read by develop with
  `AllSpec2DObj.from_fits`):
  * `chk_version=True` → `PypeItDataModelError: Current version of Spec2DObj object in code
    (1.1.1) does not match ...`. This message is misleading: Spec2DObj itself did not
    change.
  * `chk_version=False` → the same `TypeError` on `pad` as above.
* **User impact:** every `spec2d_*.fits` file produced by v2.0.x is unreadable by v2.1.0.
  That includes `pypeit_show_2dspec`, `pypeit_coadd_2dspec`, `pypeit_coadd_datacube`,
  `pypeit_sensfunc`/`pypeit_flux_calib` workflows that read spec2d, and `pypeit_ql`, even
  with `--try_old`/`chk_version=False`. Of all the issues here, this one is the most visible
  to users.

### 1.3 `FlatImages` datamodel: nested B-spline container replaced

* `pypeit/flatfield.py`: `pixelflat_spat_bsplines` and `illumflat_spat_bsplines` changed
  from `atype=pypeit.bspline.bspline.bspline` (v1.0.0, module now deleted) to
  `atype=pypeit.containers.bspline.BSplineContainer` (v2.0.0). The new container has a
  different datamodel (e.g., `bkpt_full`/`bkpt_gpm` instead of `breakpoints`/`mask`).
  **`FlatImages.version` was *not* bumped (still `1.1.2`).**
* **Round-trip result** (release-written Flat file, read by develop):
  * Both `chk_version=True` and `False` →
    `PypeItDataModelError: The HDU(s) cannot be parsed by a FlatImages object!`
    (preceded by warnings: `Error in bspline extension read: ... cannot be parsed by a
    BSplineContainer object!`).
* **User impact:** existing `Calibrations/Flat_*.fits` files cannot be reused (crash in
  `Calibrations.get_flats`). `pypeit_coadd_datacube` also cannot read the flats of release
  reductions (`coadd3d.py:1142`), and `pypeit_chk_flats` fails on old files. Because the
  version was not bumped, the error users see does not tell them that the cause is a version
  change.
* Not affected: the archived pixel flats in `pypeit/data/pixelflats` (read as raw HDUs by
  `load_pixflat`).

### 1.4 Parameter removed: `[reduce] [[cube]] align`

* `CubePar.align` (bool, default `False`) was removed and replaced by `alignment_method`
  (str, default `'phase'`; options `none`, `phase`, `cc`, `fit`, `user`).
* **Verified:** `PypeItPar.from_cfg_lines(merge_with=(['[reduce]','[[cube]]','align = True'],))`
  → `ValueError: ['align'] not recognized key(s) for CubePar.`
* There is no deprecation shim. The **release** docs (`doc/coadd3d.rst`, lines 60 and 447)
  tell users to write `align = True` in their `.coadd3d` files, so this will affect real
  input files. (The develop docs were updated.)
* **Default behavior also changed:** release defaulted to *no* alignment
  (`align = False`). Develop defaults to `alignment_method = phase`, so an unchanged
  `.coadd3d` file that never set `align` now aligns the cubes. This is not a format break,
  but the output changes.

## 2. Changes that should be judged (user-visible; borderline under the definition)

### 2.1 Pypeit-file `shift` column: changed semantics, silent

* `metadata.py`: the `shift` column type changed from `float` to `str`. A blank value means
  "no manual flexure", and any number, **including `0`**, is now a manual override
  (`pypeit_steps.py:66-75`).
* In release, `pypeit_setup --flexure` writes a `shift` column filled with `0`. Release
  ignores that column (the manual feature was lost in 2.0.0, Issue #2180).
* **Consequence:** re-running a pypeit file written by release `pypeit_setup --flexure` with
  develop pins the spatial flexure of *every* science/standard frame to 0 px. It does this
  silently, disabling the automatic spatial-flexure correction the user expected. The file
  format is still syntactically valid, but its meaning changed.
* Suggestion: if every value in the column is `0`, warn the user. Otherwise, at minimum, add
  a release-note entry telling users to blank the column.

### 2.2 Output file basenames changed for non-`.fits` raw extensions

* `PypeItMetaData.construct_basename` now calls the new `outputfiles.construct_basename`,
  which strips the longest matching `allowed_extensions` entry. The old code used
  `filename.split('.fits')[0]`.
* Verified differences (old → new root of `spec1d_*/spec2d_*` names) for spectrographs
  that exist in release:

  | spectrograph | raw file | release root | develop root |
  |---|---|---|---|
  | `aat_uhrf` | `uhrf0001.FTS` | `uhrf0001.FTS` | `uhrf0001` |
  | `mdm_modspec` | `a001.fit` | `a001.fit` | `a001` |
  | `wht_isis_blue` | `r123.fit` / `r123.fit.gz` | `r123.fit` / `r123.fit.gz` | `r123` |
  | `jwst_nirspec` | `jw01_nrs1_rate.fits` | `jw01_nrs1_rate` | `jw01_nrs1_` |

* For these instruments, re-reducing gives differently named outputs. Existing
  `.coadd1d`/`.flux`/`.coadd2d` files that list spec1d/spec2d names must be updated. This is
  arguably an improvement, but it changes output naming.
* **The `jwst_nirspec` case looks like a bug.** `'rate.fits'` and `'uncal.fits'` are listed
  without a leading `_`/`.`, so the trailing `_` is left behind. If the JWST workflow goes
  through `construct_basename`, the list should probably be `'_rate.fits'`, etc., or
  stripping should only remove the `.fits*` part.
* All `.fits`/`.fits.gz`/`.fits.bz2` instruments produce identical names (verified for
  DEIMOS, LRIS, GMOS).

### 2.3 Keck/LRIS-blue (pre-2009, `keck_lris_blue_orig`): detector labels swapped

* This is already described under "Bug Fixes". `DET01`↔`DET02` are swapped in spec2d
  extension names and spec1d object names. Users' existing `.coadd1d`/`.flux` files that
  list these object names (e.g., `SPAT0123-SLIT0456-DET01`) need the new names.
* It is a bug fix, but it changes the naming of output products, so it should be repeated
  (or cross-referenced) under "Breaking Changes".

### 2.4 Optional-dependency extra renamed: `pypeit[scikit-image]` → `pypeit[datacube]`

* `pyproject.toml`: the `scikit-image` extra is now `datacube` (scikit-image + photutils).
* `doc/installing.rst` (line 81) on develop **still says**
  `pip install "pypeit[scikit-image]"`. pip only *warns* about an unknown extra, so
  scikit-image is silently not installed. The new default `alignment_method = phase` needs
  scikit-image (otherwise it falls back to `cc`), so this ties in with 1.4.
* This is not a format break under the definition, but it changes install commands that
  users and scripts use. The docs should be fixed regardless.

### 2.5 New required dependency `pydantic>=2.0` (undocumented)

* Added to the core `dependencies` in `pyproject.toml` (it appears to be used by the new
  `pypeit.state` layer). The Dependency Changes section of `2.1.0dev.rst` lists only
  `pillow` and Python 3.14. Add `pydantic` there.

## 3. Non-breaking but should be noted in the release notes

## 4. Checked and found *not* to be breaking

* **Parameters:** apart from `CubePar.align`, all changes are additions: 26 new parameters
  and one new ParSet (`CubeExtractionPar`). No existing default changed at the ParSet level,
  and option lists only grew (`ScatteredLightPar.method += 'gaps'`, telescopes `APO`, `INT`).
* **Input-file classes** (`PypeItFile`, `FluxFile`, `Coadd1DFile`, `Coadd2DFile`,
  `Coadd3DFile`, `SensFile`, `TelluricFile`, `FlexureFile`, `Collate1DFile`, `RawFiles`):
  `required_columns`, `data_block`, `setup_required`, and `datablock_required` are
  unchanged. The block parsing is unchanged. The old leading-`|` table format now logs a
  warning instead of raising a `DeprecationWarning`, and legacy quoted colon setup values
  (`'"SINGLE:B"'`) are now auto-stripped with a warning (Issue #2099). Both are
  backwards-compatible.
* **`manual` column syntax:** the same entry (`1:1181.8:3820.6:3.;-1:1183.8:3820.6:3.:4.`)
  parses to identical results on both branches.
* **spec1d files (`SpecObjs`/`SpecObj` 1.1.14):** datamodel unchanged. A release-written
  spec1d reads in develop with `chk_version=True`. The `spec1d_*.txt` columns are unchanged.
  Object `NAME` format is unchanged for MultiSlit/Echelle/SlicerIFU; the new format applies
  only to the new `Fiber` pypeline. Primary headers gain `BUNIT` (additive).
* **Other datamodels unchanged:** `WaveCalib` (1.1.2), `WaveTilts` (1.2.0), `Alignments`
  (1.1.0), `SensFunc` (1.0.2), `OneSpec` (1.0.2), `EdgeTraceSet`, `PypeItImage`,
  `DetectorContainer` (only `det` otype narrowed from `(int, np.integer)` to `int`; spec1d
  round trip with a nested detector passes). `MultiSlitFlexure` moved modules with the
  same name/version, so file I/O is unaffected. New containers (`BSplineContainer`,
  `BSpline2DContainer`, `FiberFlatImages`, `ManualCubeExtractionObj`) are additive.
* **Collate1D:** `collate_report.dat` column definitions are unchanged. The default
  `outfile_from = 'coord'` keeps the previous naming. Disambiguation only triggers on a name
  collision (which previously overwrote silently).
* **Spectrographs:** none removed or renamed (73 → 87). No change to `camera`, `name`,
  `ndet`, `pypeline`, or `pypeit_file_keys` of existing spectrographs, except added columns
  for `mmt_mmirs` (`dithoff`, `dithpat`, `dithpos`, `frameno`). Those are added only by new
  `pypeit_setup` runs, and old files without them still run. `keck_hires` gains the `dateobs`
  meta key, which is additive. `magellan_ldss3` does not exist in release, so its "fixes"
  are not breaking.
* **Scripts:** no entry point removed. New options (`run_pypeit --ncpu`,
  `pypeit_collate_1d --outfile_from`, `--debug` on two datacube scripts) are optional.
* **Shipped data:** no files under `pypeit/data` were deleted or renamed (78 added,
  6 modified: 3 `reid_arxiv` templates, `hires_templ_pypeit.dat`, a README,
  `blackbody_info.txt`).
* **QA file naming** (`set_qa_filename`) logic is unchanged.
* **Calibration file naming** (`calibframe.py`) is unchanged.

## Recommendations

Choose one of two paths before tagging.

**Option A: keep 2.1.0 by restoring backwards compatibility.** All three datamodel breaks
look cheap to shim:

1. **`SlitTraceSet.pad`:** accept a scalar on read. For example, override
   `SlitTraceSet._parse` (or `from_hdu`) to convert an integer `pad` to `np.array([pad,
   pad], dtype=float)` before validation. Also allow 1.1.5 files to pass the version check,
   or handle the mismatch the way `DataCube.from_file` already does. This fixes Slits *and*
   spec2d files.
2. **`FlatImages` B-splines:** add a legacy reader that converts the old `bspline` v1.0.0
   HDUs (`breakpoints`, `mask`, `coeff`, `icoeff`, `nord`, `npoly`, `xmin`, `xmax`,
   `funcname`) into `BSplineContainer` (`bkpt_full`, `bkpt_gpm`, ...). Alternatively, accept
   that old flats must be rebuilt, but then **bump `FlatImages.version`** so the failure is
   a clear version-mismatch message instead of "cannot be parsed".
3. **`CubePar.align`:** accept `align` as a deprecated alias. Map `True` → `'phase'` and
   `False` → `'none'`, and log a deprecation warning. Mapping `False` → `'none'` also keeps
   release behavior for users who had explicitly set it.
4. **`shift` column:** warn (or treat as blank) when a release-era file has `shift = 0` on
   every row.

After (1)–(3), add round-trip regression tests that read small release-written files. That
will catch this class of problem in future cycles. The remaining items (2.2–2.5) would then
be release-note entries, not version-defining breaks.

**Option B: tag 3.0.0.** Populate the empty "Breaking Changes" section of
`2.1.0dev.rst` (and rename the file) with at least:

* v2.0 spec2d, Slits, and Flat files cannot be read; reprocess, and delete existing
  `Calibrations/` directories;
* `[reduce][[cube]] align` → `alignment_method` (default now `phase`);
* the changed meaning of the `shift` column;
* output-name changes for `.fit`/`.FTS` instruments and `keck_lris_blue_orig` detector
  labels.

**Either way:**

* Bump `FlatImages.version`. The nested container changed, so the version should say so.
  Also consider bumping `Spec2DObj` when its nested `SlitTraceSet` changes, so the error
  message points at the right object.
* Fix `doc/installing.rst` (`pypeit[scikit-image]` → `pypeit[datacube]`) and document the
  new `pydantic` dependency.
* Check `jwst_nirspec`'s `allowed_extensions` against the new basename logic (2.2).
* Unrelated, pre-existing, on both branches: the entry points `pypeit_install_ql_calibs`
  (`pypeit.scripts.install_ql_calib`) and `pypeit_ql_multislit` (`pypeit.scripts.ql_multislit`)
  point to modules that do not exist.
