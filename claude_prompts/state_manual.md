### 2026-08-08 (Determined the cause of Issue #2180 — manual flexure lost in the step-by-step refactor)

Read this doc, the dashboard context docs, `pypeit/state.py`,
`pypeit/scripts/pypeit_status.py`, and GitHub Issue #2180 ("Recover manual
flexure correction", reported by @Adolfo1519 via @kbwestfall).  Traced the
regression through git history.  Findings:

**The lost feature.** In v1.18.1, `PypeIt.objfind_one()` (pypeit.py, lines
~826–840) read the `shift` column of the pypeit-file data block and, if the
user had supplied a (float) value, overrode the auto-computed spatial
flexure: `sciImg.spat_flexure = np.float64(manual_flexure)`.  The manual /
auto distinction used a dtype sentinel: the column defaults to int `0`
(`metadata.py`), while user-supplied values are imposed as `float`
(`metadata.py:125`), so a float value — including `0.0` — meant "manual".
The resulting `spat_flexure` was also passed to `load_skyregions()` so user
sky regions shifted consistently.

**How it was lost (commit trail, all on the state/step-by-step refactor):**

- `37caae992` (2025-10-01, "refactor on top of pypeit"): gutted
  `pypeit.py`, removing `objfind_one()` and with it the manual-flexure
  block.
- `25eb7ca9c` (2025-08-14, "fussin and fussin"): the block *was* correctly
  ported (module-style, no `self.`) into `image_proc()` in the new
  `pypeit_steps.py`.
- `384646419` (2025-08-15, "closer now"): refactor churn removed the
  working copy from `image_proc()` and left only a stale, un-ported
  `self.`-style copy pasted inside `load_skyregions()` — dead code, since
  module-level functions have no `self`.
- `0137b8a38` (2025-11-01, "getting there"): deleted the stale copy from
  `load_skyregions()` as cleanup.  From this point the feature is gone.

**Current state (HEAD of `fix_manual`):**

- `metadata.py` still fully supports the `shift` column (typed float at
  line 125; included in pypeit-file output at 1480; defaulted to int 0 at
  1516/1552) — so users can still write `shift` values, but *nothing reads
  them*.  The feature fails silently.
- `pypeit_steps.image_proc()` builds `sciImg` and returns it with only the
  auto-computed `sciImg.spat_flexure` (from `rawimage.py`, gated by
  `spat_flexure_correct`).
- `pypeit_steps.load_skyregions()` hardcodes `spat_flexure = None`
  (line 590), a second, related regression: even auto-computed flexure no
  longer shifts user sky regions.
- Manual *extraction* (`ManualExtractionObj`, the `manual` column) survived
  the refactor (`pypeit_steps.py:857`) — only manual *flexure* was lost.
- `sciImg.spat_flexure` is still a scalar float in this datamodel
  (`pypeitimage.py:132`), so restoring the old block in `image_proc()`
  (right after the optional background subtraction, mirroring its 1.18.1
  position) is straightforward.

**Proposed fix (pending Q&A):** re-insert the ported (non-`self`) block
from commit `25eb7ca9c` into `image_proc()` in `pypeit_steps.py`, and
re-plumb `spat_flexure` into `load_skyregions()`.  Add a unit test
exercising the int-vs-float `shift` sentinel.  Questions for JXP are in the
Q&A section above.

Note: the dashboard/state context docs listed above were not implicated —
`state.py` and `pypeit_status.py` only *observe* the reduction; the
regression is in the step functions (`pypeit_steps.py`) that the state
refactor introduced.

### 2026-08-08 (Implemented the fix for Issue #2180 per Q&A answers)

Implemented on the `fix_manual` branch (confirmed to be exactly at
`origin/develop`, so the PR can target `develop` per Q&A #3).  All Q&A
answers followed: restored the feature *and* hardened the sentinel (Q1
a+b), restored the sky-regions plumbing (Q2), and validated with a
self-made dataset/pypeit file (Q4).

**Code changes (PypeIt repo):**

- `pypeit/pypeit_steps.py`:
  - New `get_manual_flexure(fitstbl, frame)` helper (with the required
    docstring/credit) that reads the pypeit-file `shift` column and
    returns the manual spatial flexure as a float, or None.  The
    hardened sentinel is NaN = "not set"; any *finite* value —
    including `0.0` — is a manual override (`np.isfinite` test).  This
    replaces the fragile 1.18.1 int-vs-float dtype test.
  - `image_proc()` now calls the helper right after the (optional)
    background subtraction — the same position the block occupied in
    1.18.1 — and, when a manual value is present, logs "Implementing
    manual flexure of X" and sets `sciImg.spat_flexure`, so the value
    propagates to object finding, sky regions, the waveimg, and the
    spec2d datamodel exactly as before.
  - `load_skyregions()` regained a `spat_flexure` parameter (it had
    been hardcoded to None), and `instantiate_objfind()` now passes
    `sciImg.spat_flexure` into it — restoring the second half of the
    1.18.1 behavior, where user sky regions shift with the frame.
- `pypeit/metadata.py`: the `shift` column default changed from
  integer `0` to `np.nan` in both `set_combination_groups()` and
  `set_user_added_columns()`.  `pypeit_setup -f` therefore now writes
  `nan` (clearly "not set") in the shift column instead of `0`, and
  `_impose_types` already coerces the column to float on read, so
  round-tripping through a pypeit file works.

**Tests:** added `test_manual_flexure()` to
`pypeit/tests/test_manual.py` covering: NaN → None, finite 2.5 → 2.5,
explicit 0. → 0. (still manual), and a missing `shift` column → None.
Ran `test_manual.py`, `test_metadata.py`, `test_inputfiles.py`,
`test_coremeta.py`, `test_setups.py` in the `pypeit14b` env (the
`pypeit14` env is missing IPython): 42 tests, all pass.

**Docs:** new "Manual correction" subsection
(`flexure-spatial-manual`) in `doc/calibrations/flexure.rst` showing
the `pypeit_setup -f` workflow and an example data block; bug-fix

**Review inventory.** The PR has one inline review comment, from Cursor
Bugbot (medium severity): "SkyRegions file ignores flexure" — when
`user_regions = 'user'`, `load_skyregions()` returns the on-disk
SkyRegions mask without applying `spat_flexure`, whereas
percentage-format regions do get the flexure via `generate_mask()`.

**Assessment: intentional behavior, not a defect.** Investigated
`pypeit/scripts/skysub_regions.py` and `pypeit/gui/skysub_regions.py`:

- The SkyRegions file is *per science frame* (its filename embeds the
  science-file basename) and is created interactively by
  `pypeit_skysub_regions` **on that same spec2d frame** — the saved mask
  is already in the frame's own pixel coordinates.
- The GUI applies the frame's recorded flexure *at creation time* via
  its `--flexure` option (it passes `spec2DObj.sci_spat_flexure` into
  `SkySubGUI`, which shifts the slit edges with
  `select_edges(flexure=...)`).
- Applying `spat_flexure` again at load time would therefore
  double-shift masks created with `--flexure`.
- Verified v1.18.1's `load_skyregions()` also returned the file-based
  mask unshifted — the PR restores exact parity.
