#### Planning

##### 2026-06-14 — Plan for richer Flats state

**Current state (what's recorded today).** `Calibrations.flats_state()`
(`calibrations.py`) records only three things on a single `FlatsState` entry:
`status='success'`, `output_file` (the merged `Flat_*.fits`), and — only if
`pixelflat_norm is not None` — `types=['pixelflat']`. `FlatsState` (`state.py`)
has just one extra field, `types: List[str]`. So the entry has **no input
files** (S2), an **incomplete `types`** that never reports illumination or
spectral-illumination corrections (S3), **no per-slit status**, and **no QA
files** — even though all of that information exists.

**What PypeIt actually produces (grounded on the 830_3460_d46 Flat file).**
The `FlatImages` product is a *merge* of up to three correction families, any
subset of which may be present:
- **pixel-to-pixel response** — `pixelflat_norm` / `pixelflat_model`.
- **spatial illumination** — `pixelflat_spat_bsplines` *or*
  `illumflat_spat_bsplines` (note: the slit-illumination correction can come
  from the *pixelflat* frames; in the 830_3460_d46 run `illumflat_*` is all
  `None` yet illumination is still corrected via `pixelflat_spat_bsplines`,
  because the dome flats serve as both and `pix_is_illum` is True).
- **spectral illumination** — `pixelflat_spec_illum` (only when
  `flatfield.use_specillum` / relative spec illum is on).
- plus **fine spatial correction** — `pixelflat_finecorr` /
  `illumflat_finecorr`.

The pixel flat has **three possible provenances**, all handled in `get_flats()`:
raw `pixelflat` frames, a **user `pixelflat_file`**, or a **slitless** pixel
flat generated on the fly (`SlitlessFlat`). Separate raw file groups feed it:
`raw_pixel_files`, `raw_illum_files`, `raw_lampoffflats` (lamp-off subtraction).

There is already a **per-slit flat status** signal, exactly parallel to
`wv_calib`/`tilts`: the `slits` bitmask carries `BADFLATCALIB`
("Flat field generation failed for this slit. Ignore it fully.") and
`SKIPFLATCALIB`, applied via `slits.mask_flats()`.

Flat **QA** is written per slit, e.g.
`Spatillum_FineCorr_<calibkey>_S<spat>_spatillum_finecorr.png` (confirmed for
S0196) and, for some instruments, `DetectorStructure_<calibkey>_*.png`.

**Data model (`state.py`) — FINAL, implemented 2026-06-14 per Q&A.** One
enriched `FlatsState` entry (Q1), `types` replaced by `corrections` (Q2), both
grouped and union input files (Q3), and **mean + RMS per correction, per slit**
(Q4+Q5), scatter-about-the-mean (Q6), `finecorr` excluded (Q7):

```
class FlatCorrectionMetric(BaseModel):          # one correction, one slit
    mean: Optional[float] = None                # np.mean over good on-slit px
    rms:  Optional[float] = None                # np.std (scatter) of the same

class FlatsSlit(BaseModel):                      # per-slit
    status: Literal["success","fail","skip","undone"] = "undone"
    corrections: Optional[Dict[str, FlatCorrectionMetric]] = \
        Field(default_factory=dict)              # keyed by correction name

class FlatsState(BaseCalibState):
    step: Literal["flats"] = "flats"
    corrections: Optional[List[str]] = []        # which corrections present:
        # 'pixelflat'  (pixel-to-pixel, pixelflat_norm)
        # 'spat_illum' (illumflat_spat_bsplines if present, else
        #               pixelflat_spat_bsplines, via fit2illumflat)
        # 'spec_illum' (pixelflat_spec_illum)
    pixelflat_source: Optional[str] = None       # 'raw'|'user_file'|'slitless'
    pixelflat_files: Optional[List[str]] = None
    illumflat_files: Optional[List[str]] = None
    lampoff_files:   Optional[List[str]] = None
    slits: Optional[Dict[int, FlatsSlit]] = Field(default_factory=dict)
```

`'flats': FlatsSlit` is added to the module's `slit_classes` map so the existing
per-slit `update_calib(..., slit=...)` machinery works for flats unchanged. The
entry-level `corrections` lists *which* corrections exist; the per-slit numbers
live on `FlatsSlit.corrections[name]`.

The inherited `input_files` (BaseCalibState) is populated with the **union** of
the raw groups (Q3) for the generic table / dashboard input list (C7); the
grouped fields give the detail panel a by-role breakdown. The inherited
`qa_files` holds the flat QA PNGs (C9). `output_file` stays the merged
`Flat_*.fits`.

**Metric definition (Q4–Q6).** Each correction's image is reconstructed exactly
as `FlatImages.show()` does, then reduced over each slit's **good, on-slit,
finite** pixels (`mean = np.mean(img[good])`, `rms = np.std(img[good])`):
- `pixelflat` → `pixelflat_norm`
- `spat_illum` → `fit2illumflat(slits, frametype='illum')` when
  `illumflat_spat_bsplines` exists, else `frametype='pixel'` (mirrors how the
  illumination is applied / the `merge` precedence)
- `spec_illum` → `pixelflat_spec_illum`

`fit2illumflat` returns 1.0 off-slit, so the on-slit restriction is required for
a meaningful `rms`. `finecorr` is intentionally **not** a separate correction
(Q7).

   determined (`self._flat_inputs = {'pixelflat':..., 'illumflat':...,

     spec_illum), computing mean/RMS as defined above, and assign the whole
     `corrections` list via `update_calib` (the Task-6 wholesale-list path
     stores a list value as-is — pydantic objects included);
   - `pixelflat_source`, the three grouped file lists, the union `input_files`,

   - per-slit `FlatsSlit.status` via `update_calib(..., slit=spat_id)` (reusing

### 2026-06-13 (Safety audit of RunPypeItState and its I/O — Task 1)

Performed Task 1 under *Safety checks*: reviewed `pypeit_workflow.md` and the
code path starting at `pypeit.py`, looking specifically for ways the new
`RunPypeItState` class and its I/O could crash a `run_pypeit` reduction. Each
of the two highest-severity findings was **reproduced** with a short script
against the installed code (no RAW_DATA needed); the rest are from reading.

**Where state is wired in (the surface that can affect a run):**
- `pypeit.py:70` constructs `run_state` in `PypeIt.__init__`; `:127`
  `required_calibs(...)` populates the `required` flags; the object is threaded
  into `calib_all` / `reduce_all` → `pypeit_steps.calib_one` → `Calibrations`
  (`state=run_state`, `calibrations.py:203`).
- `calibrations.py:run_the_steps` (`:1489`) is the hot loop: it sets
  `status='running'`, runs the step, sets success/fail, and calls
  `state.write()` on every step transition (`:1499, :1514, :1528`). This is the
  I/O that lands in the reduction's inner loop, so it is the main crash surface.
- `load()` is currently **commented out** at `pypeit.py:74` and
  `pypeit_status.py:64`, so today a run does not *read* a prior state file.

**Findings (severity in caps):**

- **C1 — HIGH, reproduced. Invalid status string `'failed'` poisons the state
  file.** `calibrations.py:1520` writes `status='failed'`, but the
  `BaseCalibState.status` Literal only allows
  `complete|fail|undone|running|success`. pydantic v2 does **not** validate on
  assignment, so the run keeps going and writes the file — but
  `RunPypeItState.load()` / `model_validate` then raises `ValidationError` on
  that file (reproduced: `Input should be 'complete', 'fail', ... input_value
  ='failed'`). Impact: any reduction with a failed calibration step produces a
  `*_state.json` that **cannot be reloaded** → the dashboard's load path (R4)
  crashes, and `run_pypeit` itself would crash on startup the moment `load()`
  (pypeit.py:74) is uncommented. **Fix: write `'fail'`, not `'failed'`.**

- **C2 — HIGH. Bare `except: embed(...)` around `state.write()`.**
  `calibrations.py:1527-1530` wraps the in-loop write in
  `try: ... except: embed(header='1551 of calibrations')`. If a write ever
  raises, the reduction drops into an **IPython embed shell mid-run**. In
  non-interactive contexts (dev suite, Nautilus/cron, `nohup`) this hangs or
  errors out the run; interactively it silently blocks the pipeline. It also
  swallows the real exception. **Fix: replace with `log.warning(...)` + continue
  — state I/O must never abort a reduction.** (A second commented `embed` sits at
  `:1367`; remove it too.)

- **C3 — MEDIUM-HIGH, reproduced. Mosaic detectors break `update_calib`
  matching → duplicated / corrupt state.** For mosaics, `det` is a tuple (e.g.
  `(1, 5)` for DEIMOS/GMOS/MOSFIRE), passed straight from
  `spectrograph.select_detectors()` (confirmed: that method returns tuples for
  mosaics). pydantic coerces the stored `det: int | List[int]` field to a list
  `[1, 5]`, so the lookup `item.calib_id == calib_id and item.det == det`
  compares `[1,5] == (1,5)` → always False. Every `update_calib` call therefore
  **creates a new entry** instead of updating the existing one. Reproduced: 3
  separate `bias` entries after 3 calls, with `running`, `success`, and the
  `mean` metric scattered across different entries. The run does not crash
  (`update_calib` never raises), but the state is bloated and wrong, and the
  dashboard view is meaningless for every mosaic instrument. The TODO at
  `state.py:154` already flags this. **Fix: normalize `det` to one canonical type
  (tuple→list) on both the stored value and the comparison key.**

- **C4 — HIGH (latent). `load()` has no schema/version guard.** When `load()` is
  re-enabled (clearly intended — see commented `pypeit.py:74`,
  `pypeit_status.py:64`), any pre-existing `*_state.json` that is partial (C1),
  hand-edited, or written by an older schema will raise `ValidationError` and
  crash `PypeIt.__init__` for **every** subsequent run in that directory until
  the file is manually deleted. PypeIt `DataContainer`s guard this with
  `chk_version`; the pydantic state has no equivalent. Also `load(path=...)`
  ignores its `path` argument (it uses `self.outfile`). **Fix: wrap `load()` in
  try/except that logs and falls back to a fresh state; add a schema-version
  field and check it.**

- **C5 — LOW-MEDIUM. The other state mutations/writes are unguarded.** The first
  two `state.write()` calls in `run_the_steps` (`:1499, :1514`) and all the
  `update_calib` calls are not protected. I verified that numpy metric values
  (`image.mean()` → `np.float64`, `np.int64` dets) currently **do** serialize
  fine, so these don't crash today — but any future state op that raises would
  abort the reduction. Given the stated goal (state I/O must never crash a run),
  a single guarded `_safe_write()` / `_safe_update()` wrapper used everywhere is
  the robust fix.

- **C6 — LOW. `required_calibs()` is now on the critical path of every run**
  (`pypeit.py:127`, unconditional, even for `calib_only`/status). It iterates
  `fitstbl.find_frames(...)`; it looks safe, but it is new code newly in
  `__init__`, so an exception there aborts startup. Worth a guard and/or
  dev-suite coverage across all three pipelines.

**Workflow-doc review:** `pypeit_workflow.md` is descriptive, not executable;
the only crash-relevant "tasks" it introduces are the state-file writes injected
into the §3.3 calibration loop and the §6.2 `*_state.json` / `*.status.log`
artifacts — i.e. exactly the `run_the_steps` write path covered by C1/C2/C5.

**Recommendations (priority order):**
1. `'failed'` → `'fail'` (C1) and delete the `except: embed` blocks, replacing
   with logged warnings (C2). These two are the concrete run/IO crashers.
2. Fix mosaic `det` matching (C3) — otherwise state is wrong for a large class
   of supported instruments.
3. Before enabling `load()`, make it crash-proof: try/except + fresh-state
   fallback + a schema version field (C4).
4. Adopt the principle that **all** state collection and I/O is wrapped so it can
   only ever log-and-continue, never abort a reduction (C5/C6).
5. Tests: add CI-safe unit tests in `pypeit/tests/` that round-trip (a) a state
   with a failed top-level step and (b) a mosaic `det` — both reproduce the bugs
   deterministically without RAW_DATA. Then exercise a mosaic spectrograph (e.g.
   `keck_deimos`) and a deliberately-failing calibration setup in the dev suite.

### 2026-06-13 (Fixed update_calib list-field handling for input_files — Task 6)

Addressed the incidental issue flagged in Task 5: `update_calib`'s list
handling was fragile for `input_files`.

**The bug.** The old "set" logic was:
`if isinstance(getattr(entry, key), list): append(value) else: setattr(value)`.
Because `input_files` (and `qa_files`) default to `None`, the *first*
`update_calib(..., 'input_files', self.raw_files)` stored the list fine — but a
*second* call (e.g. a re-run of the step) saw an existing list and `.append()`-ed
the **whole new list as one element**, producing a nested list
(`['/a.fits', ['/a.fits', '/b.fits']]`). A nested list is not `List[str]`, so it
would later fail `load()` validation — exactly the kind of I/O crash this work is
meant to prevent.

**The fix (`pypeit/state.py`, `update_calib`).** Decide by the *value* type:
- a `list`/`tuple` value (e.g. `input_files=self.raw_files`) → stored wholesale as
  a flat `list(value)` (replace). This is idempotent across repeat calls — no
  nesting.
- a scalar added to a field that *already* holds a list (e.g. flats `types`,
  default `[]`) → appended (unchanged behavior).
- otherwise → plain `setattr`.
Updated the `value` arg docstring to describe these three cases.

**Verified.** Repeat `input_files` calls now stay flat
(`['/a.fits', '/b.fits']`); `types` still accumulates
(`['pixelflat', 'illumflat']`).

**Test added.** `test_update_calib_input_files_repeat_no_nesting` in
`pypeit/tests/test_state.py`: two `input_files` updates yield a flat list of
strings that round-trips through `write()`/`load()`. Full file now **22 tests,
all passing**; lines ≤ 80; "Generated by JXP and Claude" docstring.
