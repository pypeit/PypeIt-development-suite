## Coding

Here are guidelines for coding:

- Use Python where possible
- Add inline comments to explain the effort
- Reuse existing code when possible
- Place import statements at the top of the file.
- Include a description of inputs/outputs in the doc string of all methods
- Limit lines of code to 80 characters per line
- Add "Generated by JXP and Claude" in the doc string of all methods you create
- Production Dashboard code goes in `PypeIt/pypeit/dashboard/`
- Design-phase scratch/harness code (e.g. the layout-check harness) goes in
  `PypeIt-development-suite/pypeitdev/dashboard/py/`
- Follow the GUI conventions in `pypeit_dashboard_coding.md` (qtpy-only imports;
  `Signal`/`Slot`, not `pyqtSignal`/`pyqtSlot`)

the source of truth.  A blanket signature-annotation pass over ~200 methods was
judged out of scope/risk for this PR.

**Error handling & usage docs.** Spot-checked; already solid — `safe_write` /
`safe_update_calib` wrappers, broad "never crash the derive path" try/except in

### 2026-06-30 (Fix the stale API stubs from the gui/qa module move)

Fixed the stale `doc/api/` stubs flagged above.  Confirmed the move:
`pypeit/core/gui/*` → `pypeit/gui/*`, `pypeit/setup_gui/*` →
`pypeit/gui/setup_gui/*`, and `pypeit/core/qa.py` → `pypeit/qa.py` (the new
source all imports fine).  `doc/api/` **is git-tracked** (not gitignored), so
the committed stubs must match the current layout.

**Scope check first.** Regenerated the api tree with the *exact* Makefile
`sphinx-apidoc` invocation (`--separate`, same `SPHINX_APIDOC_OPTIONS`) into a
**throwaway dir** and diffed it against the committed `api/`.  The drift was
cleanly limited to the gui/qa move — nothing else — so the fix could be
surgical rather than a full-tree regeneration (which would have churned
unrelated stubs into the PR).

**Applied (surgical):**
- Removed the 13 stale stubs: `pypeit.core.gui.*` (6), `pypeit.setup_gui.*` (6),
  `pypeit.core.qa.rst` (1).
- Added the 13 correct stubs: `pypeit.gui.*` (incl. `pypeit.gui.setup_gui.*`)
  and `pypeit.qa.rst`, taken from the fresh `sphinx-apidoc` output.
- Updated the two parent toctrees: `pypeit.core.rst` (dropped `pypeit.core.gui`
  + `pypeit.core.qa`); `pypeit.rst` (dropped `pypeit.setup_gui`, added
  `pypeit.gui` + `pypeit.qa`).
- **Left `pypeit.coadd2d.rst` untouched:** the regen wanted to overwrite it, but
  the committed version is a deliberate *manual* customization (an explicit
  ``CoAdd2dStack`` autoclass block with ``:exclude-members:``), so a blind
  apidoc regen would have silently reverted real doc work — exactly why I diffed
  to a temp dir instead of overwriting `api/` in place.

**Verify.** Rebuilt the docs the RTD way
(`sphinx-build -b html -d _build/doctrees -aE -W --keep-going . _build/html`,

(the ~24 "Failed to import" GUI/qa warnings are gone).  All 13 new modules
import cleanly under offscreen Qt.  Working-tree footprint is exactly: 2
modified toctrees, 13 deleted stale stubs, 13 new stubs.

**Note for the PR.** This same drift exists on `develop` (it has the stale
stubs and lacks `pypeit.gui.*`/`pypeit.qa.rst` too), so the move was never
reflected in the docs anywhere; this commit fixes it for the `state` branch.

**Learned.** `sphinx-apidoc` only *adds/overwrites* — it never deletes stubs for
modules that moved away, so committed api stubs rot silently after a refactor
and only a `make clean` (or manual deletion) clears them.  And it will clobber
hand-tuned api stubs (`pypeit.coadd2d.rst`), so regenerate-to-temp + selective
apply is the safe pattern when `api/` is tracked.
