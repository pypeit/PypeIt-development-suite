# PypeIt Dashboard — Alpha Phase (bug reports)

## Goals

The PypeIt Dashboard's six-stage build order (Stages 0–6) is complete and its
Stage-6 modification rounds are signed off (see `dashboard_dev_stage_6.md`).  The
project now enters the **Alpha phase**: initial testing by **outside users**.

This document drives that phase.  Unlike the stage docs (which built features to
a spec), this doc works on **bug reports** supplied as inputs — each is triaged,
diagnosed, fixed (or reported on), tested, documented, and logged.  The goal is a
tight report → diagnose → fix → verify loop that keeps the dashboard correct and
the docs/tests in step as real users exercise it.

The dashboard's design and current behavior are recorded in:

- `pypeitdev/dashboard/pypeit_dashboard_design.md` — the design (requirements
  `R#`, the status palette `R10`, the views, the `X#` execution/lock items) and
  the changelog (currently **v1.3.9**).
- `pypeitdev/dashboard/pypeit_dashboard_coding.md` — the MVC split, the build
  order, the GUI/coding conventions, the test strategy, and the
  debugging/layout-check workflow.
- `doc/dashboard/dashboard.rst` + `doc/dashboard/dashboard_design.rst` — the
  user-facing documentation (with Mermaid design diagrams) and the
  state documentation `doc/state.rst`.

## Coding

Here are guidelines for coding (carried over from the stage docs):

- Use Python where possible.
- Add inline comments to explain the effort.
- Reuse existing code when possible.
- Place import statements at the top of the file (qtpy-only imports;
  `Signal`/`Slot`, not `pyqtSignal`/`pyqtSlot`).
- Include a description of inputs/outputs in the doc string of all methods.
- Limit lines of code to 80 characters per line.
- Add "Generated by JXP and Claude" in the doc string of all methods you create.
- Production Dashboard code goes in `PypeIt/pypeit/dashboard/`; the reduction
  **state** layer is in `PypeIt/pypeit/state/`.
- Design-phase scratch/harness code (e.g. the layout-check harness) goes in
  `PypeIt-development-suite/pypeitdev/dashboard/py/`.
- Follow the GUI conventions in `pypeit_dashboard_coding.md`.

**Constraints (carried over):**

- The user stages/commits **git** themselves — do **not** run `git` commands that
  modify the repo (read-only inspection is fine).
- Dashboard code must remove/replace files via `pathlib` (`Path.unlink` /
  `Path.rename`), **never** a shell `rm`.

## Workflow

Each bug report is worked as follows (mirroring the Stage-6 Modifications
rounds):

1. **Triage / reproduce.** Read the report.  Reproduce it where possible — on the
   CI-safe fixtures, headlessly (`QT_QPA_PLATFORM=offscreen`), or on a real
   dev-suite reduction.  Prefer an automated reproduction (a `pytest` case, a
   headless model/`pytest-qt` check, or an offscreen render) over manual steps.
2. **Diagnose.** Trace the root cause in the code and write it up in that report's
   **Report** sub-section (what, where, why) — as done for the Stage-6 rounds.
   Some prompts will ask for **investigation + report only** (no code yet); honor
   that.
3. **Fix.** Make the smallest correct change at the right layer (model vs view vs
   state vs pipeline script).  Add/adjust a **regression test** that fails before
   and passes after.  Prefer fixing the root cause over a view-only patch.
4. **Verify.**
   - `python -m pytest pypeit/tests/test_dashboard.py pypeit/tests/test_state.py`
     (offscreen) — all pass; add the new test(s).
   - Re-render the relevant **screenshot(s)** via the layout-check harness when a
     fix changes appearance; review them.
   - When docs change, build them the way ReadTheDocs does — warnings are errors:
     `cd doc; sphinx-build -b html -d _build/doctrees -aE -W --keep-going . _build/html`
     → must be **exit 0, 0 warnings** (generate `pypeit_par.rst` + `help/*.rst`
     first if needed: `python ./scripts/build_par_rst.py; python ./scripts/write_script_help.py`).
5. **Document + version.** Update the user docs (`dashboard.rst` / `state.rst` /
   `scripts.rst`) when behavior changes; add a release note to
   `doc/releases/2.1.0dev.rst` for pipeline/script changes; bump the Dashboard
   version (`pypeit/dashboard/__init__.__version__` + the two `.rst`
   "Dashboard documentation version" lines + the design/coding `**Version:**` and
   changelog) together when the fix is user-visible.
6. **Log.** Record the work in this doc's **Logs** section (format below).

## Logs

### 2026-06-17 (Bug report 000 — crashed (Re)Build now shown as failed, not stuck orange)

Worked bug report 000: on a `keck_mosfire` (Re)Build of **Flats**, an injected
crash (`raise PypeItError` in `flatfield.py`) left the step **orange** and the
Build channel reporting "running" — the failure was never surfaced.

**Triage/reproduce.** The reporter's own redux dir
(`Redux/Keck/MOSFIRE/Fynbo/test_A/`) already held the smoking gun:
`keck_mosfire_A_state.json` had `current_step: flats` and `flats.status =
'running'`.  So the step was genuinely stuck at `running` on disk, not just a
view glitch.

**Diagnose.** Two defects, two layers:
1. **Pipeline.** `Calibrations.run_the_steps`
   (`PypeIt/pypeit/calibrations.py`) writes `running` before `get_<step>()` and
   only writes `fail` via the post-call `if not self.success:` branch.  An
   *exception* in the step bypasses that branch entirely, so the state is left at
   `running` (the script still exits non-zero, but the on-disk status lies).
   This is the true root cause and affects `pypeit_status` too, not just the
   Dashboard.
2. **Dashboard.** The Build channel is written by both the `Launcher` (on
   finish) and the live monitor (`view/main_window.py`).  Because a crashed
   run's `.log` mtime stays "recent" for `RunLock.ACTIVE_WINDOW_S = 10 s`, the
   lock lingers and the monitor's "Monitoring…"/"Idle" messages overwrite the
   launcher's failure message.

**Fix.**
- `calibrations.py`: wrapped `get_<step>()` in try/except that marks the step
  `fail` + `safe_write`s before re-raising → step turns **red** for any client.
- `view/main_window.py`: sticky `_last_run_failed` flag set in
  `_on_run_finished(code)`; shows "(Re)Build failed (exit code N) — see the
  log." and is no longer clobbered by the lingering live monitor; cleared when a
  new run starts.

**Verify.** Two new regression tests (both red→green):
`test_state.py::test_run_the_steps_marks_fail_on_exception` and
`test_dashboard.py::test_main_window_failed_run_marks_build_channel`.
`pytest test_dashboard.py test_state.py` → **100 passed** (offscreen).
End-to-end re-run of `pypeit_run_to_calibstep … flats --calib_group 0 --det 1`
on the MOSFIRE data: exits **1**, state `flats → 'fail'` (renders red).  Docs
rebuilt with `-W --keep-going` → exit 0, 0 warnings.

**Version/docs.** Bumped Dashboard **1.3.9 → 1.4.0** (`__init__.__version__`,
both `.rst` version lines, design+coding `**Version:**`/changelog).  Added a
crash-handling note to `dashboard.rst`'s (Re)Build section and a pipeline Bug-Fix
note to `doc/releases/2.1.0dev.rst`.

**Learned.** A step that *raises* and a step that *reports `self.success =
False`* are different failure channels in `run_the_steps`; only the latter was
handled.  And the activity bar has two writers — any "final" status message
needs to survive the live monitor's polling cadence, not just be set once.
(The reporter's artificial `raise` in `flatfield.py` is still in place; it
should be reverted before normal use.)
