# Develop Stage 4 of the PypeIt Dashboard

## Goals

Continuing the staged build defined in `pypeit_dashboard_coding.md`
(*Developing → Build order*), this document guides **Stage 4 — Execution,
Locking & (Re)generate**: the controls that let the Dashboard **launch PypeIt
work** safely, rather than only *inspect* what a reduction has already produced.

Through Stage 3 the Calibrations view is read-only: it shows each step's status,
metrics, inputs, QA, and per-slit/order detail, and launches the existing
inspection tools. Stage 4 adds the one remaining Calibrations requirement — the
**(re)generate** control (C10) — together with the cross-cutting safeguards that
make launching a run safe: a **single-run lock** (X1) and **clobber
protection/confirmation** (X2/X3). It is where a user answers "this calibration
is bad — rebuild it" without risking a concurrent run or an accidental
overwrite.

Stage 4 builds on what already exists:

- **Stage 0** — the `MainWindow` with the Status | Calibrations tab bar and the
  shared header.
- **Stage 1** — `pypeit.dashboard.model.DashboardModel` (status table,
  `(calib_id, det)` enumeration, path-aware `step_order()`, `step_metrics`,
  `slit_table`, `output_path`/`calib_file_path`, `is_stale`, spectrograph
  access).
- **Stage 2** — the `StatusView` (scope drop-downs, navigator, color+glyph
  table, Refresh).
- **Stage 3** — the `CalibrationsView` (scope selectors, path-aware step-button
  row, detail panel, per-slit/order drill-down), the **`Launcher`** (`QProcess`
  subprocess infrastructure), the **`inspect.py`** command builders, and the
  shared **`ActivityBar`** status/activity area (X4/X5, already delivered).

Stage 4 stays thin on the GUI side and **reuses existing PypeIt machinery** for
execution: it launches the existing `pypeit_run_to_calibstep` script (which
wraps `PypeIt(..., calib_only=True)` → `calib_one(..., stop_at_step=…)`) through
the **same `Launcher`** built in Stage 3, rather than re-implementing any
calibration logic.

**Scope note (what is *not* in Stage 4).** Live **monitoring**/auto-refresh
while a reduction runs is **Stage 5** (R14); a populated **Science-frames**
section is **Stage 6**. A full "Run reduction" (`run_pypeit`) action is noted in
the design as the same locking concern but is **not** part of Stage 4 — Stage 4
targets the per-step (re)generate path. The Deferred items CD1–CD3 (queuing /
in-run launch, parameter editing, side-by-side comparison) and XD1–XD2 (queuing,
cancel/abort) remain out of scope.

Each stage below carries the design requirements it satisfies (the `C` / `X`
items in `pypeit_dashboard_design.md`), a concrete task breakdown, the files it
touches, and acceptance criteria. Open implementation choices are raised in the
**Clarifications** channel for the user to answer inline before coding begins.

### Stage 4 — Execution, Locking & (Re)generate

**Design refs:** C10 (a (re)generate control, enabled only when PypeIt is idle,
launching `pypeit_run_to_calibstep` for the selected step with
`--calib_group`/`--det`, in a distinct **action** color), C15 (the launch is
**observable** and the state/buttons **refresh** on completion), X1 (single-run
lock — at most one active PypeIt process; disable all launch controls while one
runs; detect an *out-of-Dashboard* run via the reduction `.log` mtime), X2
(clobber **confirmation** — a warning naming the file(s) that will be
overwritten + explicit confirm), X3 (clobber **capability** — overwrite only the
**selected step's** output, reusing preceding steps). Builds on X4/X5 (the
`ActivityBar`, already delivered in Stage 3).

**Goal.** Add the (re)generate control to the Calibrations detail panel and the
execution safeguards around it, reusing the Stage 3 `Launcher`/`ActivityBar` and
the existing `pypeit_run_to_calibstep` backend. No new view; this extends the
Calibrations view and the model/launcher.

**Proposed layout / mechanism** (subject to the Clarifications):

1. **(Re)generate control** (C10) — a button in the detail panel for the selected
   step (placement TBD — S4-Q1), in a distinct **action color** (not a status
   color, so it is never mistaken for "success" — magenta/the selection accent or
   a neutral action style). Enabled only when (a) the step has a real output to
   regenerate and (b) the Dashboard is **unlocked** (X1).
2. **Run-command builder** — extend `inspect.py` (or a small sibling) with a
   builder returning the `pypeit_run_to_calibstep` argv for `(step, group, det)`
   — always passing `--calib_group` and `--det` and the `.pypeit` file /
   `--redux_path`, never the `--science_frame` form.
3. **Single-run lock** (X1) — a small **lock controller** (model- or
   launcher-level, Qt-free where possible) that (a) knows when *the Dashboard*
   launched a run (via the `Launcher`/`QProcess` lifecycle) and (b) detects an
   **external** run by watching the reduction `.log` **mtime** (advancing ⇒
   active). While locked, every launch control is disabled and the `ActivityBar`
   shows the active task; on completion the lock releases and the state refreshes
   (per R12: read `*_state.json` while running, re-derive when idle).
4. **Clobber confirmation + capability** (X2/X3) — before launching a
   regeneration that would overwrite existing output(s), a **confirmation
   dialog** naming the exact file(s) (from `model.output_path`/`calib_file_path`)
   that will be removed/overwritten; on confirm, the **selected step's** output
   is cleared and `pypeit_run_to_calibstep` is run (reusing the preceding steps).
   The clobber mechanism through `run_to_calibstep` (which today only reuses) is
   open — see S4-Q3.
5. **Observability + refresh** (C15) — the run reports start/progress/outcome via
   the `ActivityBar` (busy indicator while running), and on completion the
   Calibrations (and Status) view **re-reads the state and re-colors** the
   buttons/table.

**Deliverables / tasks.** *(to be finalized after the Clarifications)*

1. **(Re)generate button** in `view/calibrations_view.py` — action-colored,
   idle-gated, wired to the lock + clobber-confirm + launcher.
2. **Run-command builder** in `inspect.py` — `run_to_calibstep` argv for the
   selected `(step, group, det)`.
3. **Lock controller** — single-run lock with `.log`-mtime external-run
   detection; disables/enables all launch controls; surfaces the active task to
   the `ActivityBar`.
4. **Clobber confirmation dialog + capability** — name-the-files warning; clobber
   only the selected step's output; the `run_to_calibstep` overwrite path
   (mechanism per S4-Q3).
5. **State refresh on completion** (C15) — re-derive/re-read and re-render both
   views when a run finishes (and the lock releases).
6. **Tests** — CI-safe `pytest` (no real `run_pypeit`): the run-command builder
   argv; the lock state machine (idle → locked → released; external-run
   detection via a synthesized advancing-`.log` mtime); the clobber dialog's
   file-naming; the button's idle-gating. Mock/stub the actual subprocess.
7. **Harness / screenshots** — render the (re)generate control + the
   confirmation dialog + the locked (disabled) state across light/dark for the
   milestone screenshots.

**Acceptance criteria.** *(to be finalized after the Clarifications)*

- The selected step shows a (re)generate control in a distinct action color,
  enabled only when the Dashboard is idle and the step is regenerable.
- Launching a regeneration runs `pypeit_run_to_calibstep <pf> <step>
  --calib_group <id> --det <det>` (verified by the builder test + interactive
  launch); preceding steps are reused, only the selected step is overwritten.
- While a run is active (Dashboard-launched **or** detected via an advancing
  `.log` mtime), all launch controls are disabled and the `ActivityBar` shows
  the active task; on completion controls re-enable and the views refresh.
- A clobber shows an explicit confirmation naming the file(s) to be overwritten;
  cancelling aborts without touching disk.
- CI-safe tests pass offscreen; light/dark renders legible.
