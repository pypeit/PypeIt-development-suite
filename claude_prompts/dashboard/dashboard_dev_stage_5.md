# Develop Stage 5 of the PypeIt Dashboard

## Goals

Continuing the staged build defined in `pypeit_dashboard_coding.md`
(*Developing → Build order*), this document guides **Stage 5 — Monitoring (live
updates)**: while a reduction is **running**, the Dashboard should reflect its
progress in (near) real time, rather than only when the user clicks **Refresh**.

Through Stage 4 the Dashboard can *launch* a (re)build and *refresh once* when it
finishes, and it already **detects an active run** — Dashboard-launched **or**
started in a terminal — via the `RunLock` (the reduction `.log` mtime). Stage 5
turns that detection into **continuous monitoring**: while a run is active, the
state views **auto-update** as PypeIt writes `*_state.json` on each step
transition, so the user watches calibrations turn from white → orange → green
without touching the UI. It is the design's R14 ("live status updates").

Stage 5 builds on what already exists:

- **Stage 1** — `DashboardModel` (loads `*_state.json`; `status_table()`,
  `slit_table`, `step_metrics`, `is_stale`, `log_path`).
- **Stage 2** — the `StatusView` (summary strip, navigator, color+glyph table,
  manual **Refresh** that re-acquires the model).
- **Stage 3** — the `CalibrationsView` (step-button row, detail panel) and the
  shared **`ActivityBar`** (X4/X5).
- **Stage 4** — the **`RunLock`** (already polls the `.log` mtime every ~2.5 s
  and emits `lockChanged`), the **`Launcher`**, and the **refresh-on-completion**
  path (`CalibrationsView.refresh()` preserves scope + selected step; the Status
  view re-renders).

Stage 5 stays thin and **reuses the existing state-file feed** — no new pipeline
instrumentation: `pypeit/calibrations.py` already writes `*_state.json` on every
step transition (sets `status='running'` before a step, `'success'`/`'failed'`
after, calling `state.write()` each time; coding doc *Monitoring an active
reduction*). The Dashboard just needs to **notice the file changed and
re-render**.

**Scope note (what is *not* in Stage 5).** A populated **Science-frames**
section is **Stage 6**. Launching a **full `run_pypeit`** from the Dashboard
stays **deferred** (v1 only *observes* full runs; coding doc *Launch scope*).
The previously-prototyped `log.step` broadcast hook is **not** used (it was
removed from `state.py`); monitoring rides the **state-file feed**, not a
log-stream channel.

Each stage below carries the design requirements it satisfies (the `R` items in
`pypeit_dashboard_design.md`), a concrete task breakdown, the files it touches,
and acceptance criteria. Open implementation choices are raised in the
**Clarifications** channel for the user to answer inline before coding begins.

### Stage 5 — Monitoring (live updates)

**Design refs:** R14 (live status updates while a reduction is running), R12
(refresh source — read `*_state.json` while running, re-derive when idle), R13
(the stale indicator interplay). Builds on the Stage 4 `RunLock` (active-run
detection) and the refresh-on-completion path.

**Goal.** While a run is active, **auto-refresh** the Status and Calibrations
views from `*_state.json` as PypeIt writes it, with no manual Refresh — reusing
the existing model-reacquire + view-rerender path and preserving the user's
scope/selection. Stop when the run ends (one final refresh, then idle).

**Mechanism** (resolved by the S5-Q answers; **always-on while running**,
S5-Q7):

1. **Active-run detection** — already in `RunLock` (the `.log` mtime poll +
   `lockChanged`). Monitoring is active exactly while the lock is engaged
   (Dashboard-launched **or** an external run, incl. a run already in progress
   when the Dashboard launches).
2. **State-change detection** — a **single ~2 s `QTimer` poll** of the
   `*_state.json` **mtime**, reusing the `RunLock` tick (S5-Q1/Q2: poll, one
   timer). `RunLock` gains a **`stateChanged` signal** (S5-Q3): on each tick,
   while active, if the state file's mtime advanced since the last tick, emit
   `stateChanged`. No `QFileSystemWatcher`.
3. **Live re-render** — on `stateChanged`, re-acquire the model **reading the
   state file** (R12; never re-derive mid-run) and re-render **both** views,
   **preserving** the current scope + selected step via
   `CalibrationsView.refresh()` (Status view re-renders in place). Re-render
   **only when the mtime actually advanced** (not every tick), so it does not
   churn the panel the user is reading. The user can still **inspect
   already-built calibrations while later steps build** (S5-Q4) — inspection
   (`Launcher.launch()`) is not gated by the lock.
4. **Completion** — when the lock releases (run finished/stalled), do one
   **final** refresh and return to idle (this subsumes the Stage 4
   refresh-on-completion: `_on_run_finished` becomes the same "refresh from
   state" slot the monitor uses).
5. **Two-channel ActivityBar** (S5-Q5/Q9) — split the one status bar into a
   **Build** channel (the (Re)Build run + live "Monitoring…" + busy spinner) and
   an **Inspection** channel (user viewer launches + its own spinner), so
   build/monitoring status and inspection feedback never overwrite each other.
6. **`.log` tail view** — **deferred** (S5-Q6); Stage 5 is the state-driven
   auto-refresh only.

**Deliverables / tasks.**

1. **`RunLock.stateChanged`** — extend the existing poll: track the
   `*_state.json` mtime and emit `stateChanged` when it advances while active.
   Keep the mtime comparison a pure, testable method (like `_is_recent`).
2. **`MainWindow` wiring** — factor the Stage-4 `_on_run_finished` body into a
   reusable **`_refresh_from_state()`** slot (re-acquire model + re-render both
   views, preserving scope/selection); connect `RunLock.stateChanged` →
   `_refresh_from_state`, and keep the final completion refresh on lock release.
3. **R12 source rule** — while active, the refresh **loads** the state file (it
   is present during a run); idle behavior unchanged.
4. **Two-channel `ActivityBar`** (S5-Q9) — Build + Inspection regions, each with
   a message + busy indicator; route `Launcher.run()` → Build,
   `Launcher.launch()` → Inspection, the monitor's "Monitoring…" → Build, and
   the Status-view Refresh source message → Build.
5. **Tests** — CI-safe per S5-Q8: stage a `*_state.json`, build the window,
   rewrite the file (flip a step `running`→`success`) + bump mtime, **call the
   poll directly** (no wall-clock wait), and assert `stateChanged` fires, both
   views re-render, and scope/selection is preserved; assert no `stateChanged`
   when idle or when the mtime is unchanged.
6. **Harness / screenshots** — render a "mid-run" state (a step `running`,
   orange) and the two-channel status bar for the milestone screenshots.

**Acceptance criteria.**

- While a run is active, the Status table/summary/navigator and the Calibrations
  button row update **without** a manual Refresh as `*_state.json` changes.
- The live refresh **preserves** the user's scope (group/detector) and selected
  step, and re-renders **only** when the state file actually changed.
- The user can **inspect** already-built calibrations while later steps build;
  inspection feedback uses its **own** status channel (does not clobber the
  build/monitoring status).
- Mid-run reads come from the **state file** (R12), not a re-derive.
- Monitoring **starts** when a run begins (Dashboard-launched or external) and
  **stops** with one final refresh when it ends; no busy-spin when idle.
- CI-safe tests pass offscreen.

**Round 2 findings — a read-only derive writes a stale "running" state
(Modifications R2 #1).**

*Investigated 2026-06-15. Root cause confirmed; fix deferred to S5-Q12.*

- **Symptom.** Launch the Dashboard on a reduction with calibrations on disk but
  **no** state file → close → relaunch → the state file shows the "current step"
  as `flats` (running).
- **Root cause.** With no state file the model **derives**
  (`PypeIt(...).calib_all(status_only=True, reload_only=True)`).
  `calibrations.run_the_steps` writes `*_state.json` at its start (~1692) and
  before each step after setting `'running'` (~1707) — **both unconditional** —
  but **skips** the post-step write (~1729) when `status_only`. So each step is
  re-persisted as `success` by the *next* step's write, except the **last** step
  (`flats`), whose `'running'` is never overwritten; `current_step` is left at
  `flats`. **Reproduced:** the derive wrote `current_step=flats`,
  `flats.status=running` (while `arc.status=success`). On relaunch the model
  *loads* that file → shows `flats` running. So a **read-only status derive is
  mutating the persisted state** — the real defect (it also overwrote the
  otherwise-good state file).
- **Proposed fix.** Make a status-only pass not leave a misleading file — see
  **S5-Q12** (I lean **(A)**: don't write at all during `status_only`, so a
  derive is truly read-only; no `state.py` schema change). Awaiting your choice
  before touching `calibrations.py`/`state.py`.
- *(Aside: the derive also logs `PydanticSerializationUnexpectedValue` for
  `output_file` being a `PosixPath` rather than `str` — harmless today but worth
  coercing to `str` when we next touch the write path.)*
