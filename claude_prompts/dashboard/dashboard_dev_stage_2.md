# Develop Stage 2 of the PypeIt Dashboard

## Goals

Continuing the staged build defined in `pypeit_dashboard_coding.md`
(*Developing → Build order*), this document guides **Stage 2 — the
Initialization / Status view**: the dashboard's landing, *state-first* view
that answers "where does this reduction stand?" at a glance.

Stage 2 builds on the artifacts already delivered:

- **Stage 0** (walking skeleton) — the `pypeit_dashboard` launcher, the
  `MainWindow` with the Status | Calibrations tab bar, and the shared header
  banner + logo. The Status tab is currently an empty placeholder.
- **Stage 1** (headless state layer) — `pypeit.dashboard.model.DashboardModel`
  (source-priority state acquisition, the normalized status table, the
  `(calib_id, det)` enumeration, the path-aware step order, edge-state
  reporting) and `pypeit.dashboard.palette` (the Qt-free status palette).

Stage 2 turns the Status tab placeholder into the real view by **consuming**
that model — it adds **no new PypeIt-facing logic**; the view is thin (per the
MVC split in the coding doc) and renders what the model provides.

Stages 0 and 1 are documented in `dashboard_dev_stages_0-1.md`; later stages
(Calibrations view, Execution/Locking, Monitoring, Science frames) get their own
documents.

Each stage below carries the design requirements it satisfies (the `R` items in
`pypeit_dashboard_design.md`), a concrete task breakdown, the files it touches,
and acceptance criteria. Genuinely open implementation choices are raised in the
**Clarifications** channel for the user to answer inline before coding begins.

### Stage 2 — Initialization / Status view

**Design refs:** R3 (color-coded state table), R7 (at-a-glance summary), R8
(grouped/ordered, scoped rows), R9 (required vs optional clarity), R10
(color + glyph, never color alone), R11 (graceful empty/edge states), R12
(manual refresh), R13 (stale-state indication), R15 (science-frame readiness —
designed-for, placeholder), R16 (scope drop-downs), R17 (configuration-overview
navigator grid), R18 (equally-prominent, scalable Science section — placeholder).

**Goal.** Replace the Status-tab placeholder with the real, *state-first*
landing view, rendering the Stage 1 `DashboardModel`. It reuses the
Dashboard-wide palette (light/dark) and stays thin — no PypeIt logic in the
widgets.

**Proposed layout** (top → bottom, per the design's *Default State View*; the
shared header banner from Stage 0 sits above all of this):

1. **Global summary strip** (R7) — whole-run health (e.g. "Calibrations: 6/6
   required success" + counts of fail / running / undone), always visible.
2. **Scope toolbar** (R16) — calibration-group and detector/mosaic drop-downs
   (from `model.calib_det_pairs()`), plus a filter control (e.g. *required
   only* / *failures only*) and a **Refresh** button (R12); a **stale** badge
   (R13) when the state file is older than the `.pypeit`/outputs.
3. **Configuration-overview navigator** (R17) — a compact `(group × detector)`
   grid, each cell colored by the *worst* step status in that cell; clicking a
   cell sets the drop-downs (click-to-scope). A single cell for a
   single-group/single-detector run (e.g. Kast).
4. **Calibrations section** (R3/R8) — the scoped state **table** for the
   selected `(group, detector)`: columns **Step | Required | Status | Output**,
   each status as **color + glyph** (R10) from the palette, with required-vs-
   optional clarity (R9), step names in pipeline order (`model.step_order()`),
   file names monospace.
5. **Science frames section** (R15/R18) — equal-weight heading, a **placeholder**
   for now (the state model does not yet track science frames); designed so it
   can be populated later without redesign.

**Deliverables / tasks.**

1. **`StatusView` widget** (replace `view/status_view.py` placeholder) — takes a
   `DashboardModel` (+ theme), builds the layout above, and re-renders on scope
   change / refresh. Thin: all data via the model; all colors/glyphs via
   `palette`.
2. **State table** (R3, R8, R9, R10) — render `model.status_table()` filtered to
   the selected `(group, detector)`, ordered by `model.step_order()`, with the
   palette color + glyph per row and required/optional distinction.
3. **Global summary strip** (R7) — derive counts from the full
   `model.status_table()` (across all scopes), generalizing to science later.
4. **Scope drop-downs** (R16) — populate from `model.calib_det_pairs()`; changing
   either re-renders the table (and the navigator selection).
5. **Configuration-overview navigator grid** (R17) — `(group × detector)` cells
   colored by worst status; click-to-scope wiring to the drop-downs.
6. **Manual refresh** (R12) — re-acquire the state via the model and re-render.
   (The "source depends on whether a run is active" nuance and live updates are
   Stage 4/5; Stage 2 does a manual re-acquire.)
7. **Stale-state indicator** (R13) — flag when `*_state.json` is older than the
   `.pypeit` file or the calibration outputs.
8. **Empty/edge states (R11)** — render `model.load_status`
   (`not_started` / `malformed` / `file_not_found` / `error`) as a clear,
   centered message with a next action, not an empty grid.
9. **Science section placeholder** (R15/R18) — equal-weight heading + "tracked
   in a future stage" stub.
10. **Wire-in** — `app.launch` / `MainWindow` build a `DashboardModel` (which
    already holds `header_info`) and hand it to the `StatusView`.
11. **Theme-aware rendering** — use the palette's light/dark sets; verify via the
    render matrix.
12. **Layout-check harness extension + structural `pytest-qt` tests** — render
    the Status view across light/dark × default/resized with the fixtures
    (healthy / partial / failed / not-started) and assert structure (columns,
    drop-downs, summary, navigator). Produce milestone screenshots.

**Acceptance criteria.**

- With a healthy fixture state, the Status view shows the summary strip, the
  scope drop-downs (Kast: one group/detector), the navigator (single green
  cell), and the scoped table with correct color+glyph per step.
- Changing the scope drop-downs (or clicking a navigator cell) re-scopes the
  table; the summary strip stays whole-run.
- The four edge cases (`not_started`, `malformed`, `file_not_found`, a `fail`
  step) each render clearly (message or red ✗ row), no exceptions.
- Light and dark renders both legible; structural `pytest-qt` tests pass
  offscreen.

#### Clarifications

*(Discussion channel for Stage 2. Recommendations and open questions below —
please answer inline under each **S2-Q**. No code is written until these are
resolved.)*

- **S2-Q1 — State-table widget.** Use a simple `QTableWidget` for the scoped
  state table (one `(group, detector)` at a time → few rows), rather than a
  `QTableView` + `QAbstractTableModel` like `setup_gui`? I lean toward
  `QTableWidget` for Stage 2 (simpler, the table is small and re-rendered on
  scope change); we can graduate to a model/view later if needed.

- **S2-Q2 — Navigator grid (R17) now or minimal?** Build the
  `(group × detector)` navigator as a general, click-to-scope grid now (it is a
  single cell for Kast but scales to MOS/mosaic heat-maps), or start with a
  minimal single-cell stub and generalize later? I lean toward building it
  generally now, since R17 is core to the state-first view.

- **S2-Q3 — Launch wiring & deriving at startup.** Stage 2 should have
  `app.launch`/`MainWindow` construct a `DashboardModel` (it already carries
  `header_info`) and pass it to the view. At launch, if no state file is
  present, the model **derives** the state (R5), which needs RAW_DATA and may
  briefly block the UI (design says acceptable). OK to derive at launch, or
  should Stage 2 default to load-only and offer a "compute state" action?

- **S2-Q4 — Stale-state heuristic (R13).** Flag "stale" when the
  `*_state.json` mtime is older than the `.pypeit` file or the newest
  `Calibrations/` output. Agree with that heuristic, and a non-blocking badge
  (not a blocking dialog)?

- **S2-Q5 — Refresh semantics (R12).** For Stage 2, **Refresh** re-instantiates
  the model (re-load the state file if present, else re-derive) and re-renders.
  The active-run-aware source selection and continuous live updates are deferred
  to Stage 4/5. Confirm.

- **S2-Q6 — Science section.** Scaffold the Science section as an
  equal-weight-heading **placeholder** only (populated in the later
  science-frames stage once `RunPypeItState` tracks it), per the S0/Stage-6
  decision. Confirm.

- **S2-Q7 — Summary-strip content (R7).** Propose: "Calibrations: N/M required
  succeeded" plus small counts of fail / running / undone (optional steps noted
  separately). Good, or do you want a different headline?

- **S2-Q8 — Filter control.** Include a simple filter (e.g. *required only* /
  *failures only*) in Stage 2, or defer filtering to a later polish pass?

- **S2-Q9 — `det` formatting in the view (per S1-Q4/Q9).** The model leaves
  `det` raw (int or mosaic tuple); the view formats it. Use
  `spectrograph.get_det_name(det)` (→ `DET01`) for single detectors and a
  mosaic label (e.g. `MSC01` / `(1,5)`) for tuples, in the drop-downs and
  navigator? (The view can reach the spectrograph via the `.pypeit` file, or we
  expose it on the model.)
