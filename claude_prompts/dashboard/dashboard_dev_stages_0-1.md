# Develop Stages 0 and 1 of the PypeIt Dashboard

## Goals

We will develop the PypeIt Dashboard in stages, following the build order
defined in `pypeit_dashboard_coding.md` (the *Developing* section). This document
guides the first two stages:

- **Stage 0 — Walking skeleton.** A launchable, but mostly empty, application,
  started **like every other PypeIt script** (the `pypeit_dashboard` console
  script, using the same `ScriptBase` pattern as `run_pypeit.py`): a required
  `.pypeit` launch argument, and a `MainWindow` with the tab bar
  (Status | Calibrations), the shared header banner, and the PypeIt logo —
  reusing the `setup_gui/` application/font/icon bootstrap. The two tab views are
  empty placeholders.
- **Stage 1 — State data layer (headless).** The Qt-free model layer that loads
  or derives the reduction state and exposes it as a clean, testable API
  (status DataFrame, `(calib_id, det)` enumeration, palette/glyph mapping,
  path-aware step order, edge-state handling). No Qt.

We build Stages 0 and 1 **together** (per the coding doc's "what is implemented
first"): a launchable skeleton plus the headless state layer. Stage 2 (the
Status view) consumes Stage 1's API and is handled in a subsequent document.

Each stage below carries the design requirements it satisfies (the `R` items in
`pypeit_dashboard_design.md`), a concrete task breakdown, the files it
touches, and acceptance criteria. Genuinely open implementation choices are
raised in the per-stage **Clarifications** channels for the user to answer
inline before coding begins.

### Proposed package layout

The module layout for `PypeIt/pypeit/dashboard/`, mirroring `setup_gui/`'s
MVC organization (**approved**, S0-Q1).

```
pypeit/scripts/pypeit_dashboard.py   # RunDashboard(ScriptBase) — the launcher
                                     #   (like run_pypeit.py); main() calls app.py

pypeit/dashboard/
├── __init__.py
├── __main__.py          # optional convenience: `python -m pypeit.dashboard`
├── app.py               # application bootstrap (reuses setup_gui's)
├── model.py             # Stage 1: headless state/data layer (NO Qt)
├── palette.py           # Stage 1: Dashboard-wide status palette + glyphs
├── controller.py        # wiring + (later) subprocess launching
├── view/
│   ├── __init__.py
│   ├── main_window.py   # MainWindow: tab bar + shared header banner/logo
│   ├── header.py        # the shared header banner + logo widget (R6)
│   ├── status_view.py   # Stage 2 (placeholder in Stage 0)
│   └── calibrations_view.py  # Stage 3 (placeholder in Stage 0)
└── images/
    └── pypeit_logo.png  # logo asset shipped with the package (R6)
```

**Launch mechanism (S0 resolution).** The Dashboard is launched **exactly like
the other PypeIt command-line scripts**: through the existing
`pypeit/scripts/pypeit_dashboard.py` `RunDashboard(ScriptBase)` class, registered
as the `pypeit_dashboard` console entry point in `pyproject.toml` (the same
`ScriptBase.entry_point` pattern as `run_pypeit`). Its `main()` builds the
`QApplication` (via `app.py`, reusing the `setup_gui` bootstrap) and shows the
`MainWindow`. A thin `__main__.py` (`python -m pypeit.dashboard`) may be added as
a convenience but is **not** the primary launch path.

The reference prototype and associated files have been git-moved to
`pypeit/dashboard/prototype/` (S0-Q4); they are **not** carried forward and will
be **deleted later** once the new skeleton lands.

### Stage 0 — Walking skeleton

**Design refs:** R1 (launches via a Python script), R2 (launched from a folder
with a `.pypeit` file; the `.pypeit` file is a **required** launch argument),
R6 (shared header banner with `.pypeit` name, `PYP_SPEC`, setup/config ID,
reduction path, reduction directory, and the PypeIt logo top-right).

**Goal.** Produce a launchable, mostly empty application so the layout-review
process can exercise real widgets from day one. No reduction logic yet — the
views are placeholders and the header is populated from cheap, already-available
metadata (the `.pypeit` file + spectrograph), not from the state.

**Deliverables / tasks.**

1. **Entry point + argument parsing (R1, R2).**
   - Launch via the **`pypeit_dashboard` console script** — the
     `RunDashboard(ScriptBase)` class in `pypeit/scripts/pypeit_dashboard.py`,
     using the same `ScriptBase`/`entry_point` pattern as `run_pypeit.py`. Fix
     its `name()` (currently `'run_dashboard'`) to `'pypeit_dashboard'`; its
     `main()` launches the app (`app.py`). A `__main__.py`
     (`python -m pypeit.dashboard`) is an optional convenience, not the primary
     path.
   - The `.pypeit` file is a **required positional** argument (R2, S0-Q2),
     replacing the prototype's optional `-f/--pypeit_file`.
   - Keep `--redux_path` (testing aid) if useful.
2. **Application bootstrap (reuse `setup_gui`).** Reuse the
   application/font/window-icon/theming setup used to launch the setup GUI
   (`setup_gui/controller.py`'s `start_gui` path). Factor out a shared bootstrap
   only if low-friction; otherwise call/adapt it (S0-Q3).
3. **`MainWindow` shell.**
   - A tab bar with exactly two tabs: **Status** and **Calibrations**.
   - Each tab holds an empty placeholder widget (a labeled stub).
   - Default window size ≈ **1650×900** (the size used by the layout sketches).
4. **Shared header banner + logo (R6).** A `header.py` widget, shared by both
   tab views, showing the `.pypeit` file name, `PYP_SPEC` (spectrograph), the
   setup/configuration ID, the reduction **path** (MultiSlit / Echelle / IFU),
   and the reduction directory. The **PypeIt logo** sits in the **top-right
   corner**, clear of the banner text. Logo asset handling per S0-Q5.
5. **Loud failures (from the Debugging plan).** Install the global
   `sys.excepthook` (and the optional slot-wrapping decorator) now, so the very
   first interaction bugs surface with full tracebacks rather than being
   swallowed by the Qt event loop.
6. **Layout-check harness (Stage 0 slice).** A harness in
   `pypeitdev/dashboard/py/` that imports the real `MainWindow`, builds it with
   the `shane_kast_blue` 600/4310 example, and grabs it offscreen to a PNG across
   the light/dark × default/resized matrix (per the coding doc). Used for the
   self-check + milestone screenshot.
7. **Structural `pytest-qt` tests (written alongside).** Assert the structure:
   the tab bar is exactly `Status | Calibrations`; the header banner exposes the
   five R6 fields; the window constructs offscreen without error. Live in
   `PypeIt/pypeit/tests/` (CI-safe).

**Acceptance criteria.**

- `pypeit_dashboard <file>.pypeit` (and, if added, the optional
  `python -m pypeit.dashboard <file>.pypeit`) launches a window with the two tabs
  and a populated header banner + logo.
- A missing/omitted `.pypeit` positional argument is a clean argparse error (R2);
  the empty/edge handling of a *named-but-absent* file is shared with Stage 1
  (R11).
- The offscreen render matrix produces PNGs that match the header/tab layout in
  the design sketches; structural tests pass under `pytest-qt` offscreen.

### Stage 1 — State data layer (headless)

**Design refs:** R4 (if `*_state.json` is present, load it via
`RunPypeItState.load()`), R5 (otherwise derive it as `pypeit_status.py` does —
`PypeIt(calib_only=True).calib_all(status_only=True, reload_only=True)`; may
briefly block on launch), R11 (graceful empty/edge states: named `.pypeit` not
found; valid `.pypeit` but no state/outputs ("not started"); malformed/partial
state file).

**Goal.** A **Qt-free** model layer that is the single source of truth the views
consume. All PypeIt-facing logic lives here so it is unit-testable with plain
`pytest` (no display, and — for the load path — no RAW_DATA). The views stay
thin.

**Deliverables / tasks.**

1. **State acquisition with source priority (R4 → R5).** A model class
   (working name `DashboardModel`) that, given the `.pypeit` file and reduction
   directory:
   - loads `<pypeit_root>_state.json` via `RunPypeItState.load()` when present
     (fast path, R4); else
   - derives the state the `pypeit_status.py` way
     (`PypeIt(calib_only=True).calib_all(status_only=True, reload_only=True)`,
     reading `pypeIt.run_state`) — no processing performed (R5).
   - Records **which source** was used (for the stale-state / refresh logic in
     Stage 2's R12/R13).
2. **Status table.** Expose the existing `RunPypeItState.get_status()` DataFrame
   (columns: `calibration_group`, `detector`, `steps`, `required`, `status`,
   `output_file`) rather than re-deriving it. Add only thin convenience
   accessors the views need.
3. **`(calib_id, det)` enumeration.** Enumerate the calibration-group and
   detector/mosaic pairs present in the state, to populate the Stage 2 scope
   drop-downs and the Stage 3 selectors (R16/C2).
4. **Palette/glyph mapping (`palette.py`).** A Qt-free mapping from
   `(required, status)` (+ whether a step is in `default_steps()`) to the
   **Dashboard-wide status palette** color + glyph, exactly as tabulated in the
   design doc (success ✓ green, running ⏳ orange, fail ✗ red, required-undone ○
   white, optional – grey, n/a – dimmed grey). Returns plain data (hex + glyph +
   label), no `QColor`.
5. **Path-aware step order.** Expose the spectrograph's
   `Calibrations.default_steps()` order (MultiSlit/Echelle vs IFU), with `bpm`
   handling per the design (executed internally; omitted from the button row).
   This is consumed by the Stage 3 button row but lives in the model.
6. **Edge/empty states (R11).** Define explicit, typed results for: named
   `.pypeit` file not found; valid `.pypeit` but no state and no outputs ("not
   started"); malformed/partial `*_state.json`. The views render these as clear
   messages (Stage 2) rather than crashing.
7. **Tests + fixtures.** Headless `pytest` in `PypeIt/pypeit/tests/`, driven by
   committed `*_state.json` fixtures in `pypeit/tests/files/` (healthy
   `shane_kast_blue` 600/4310 + crafted edge cases: not-started, partial, one
   failed step, malformed). The **derive** path (R5) needs RAW_DATA, so its test
   runs in the dev suite (`unit_tests/`); the **load** path and all
   mapping/enumeration logic are CI-safe in the main repo (see S1-Q3).

**Acceptance criteria.**

- Given a fixture `*_state.json`, the model loads it and returns the status
  DataFrame, the `(calib_id, det)` list, and correct palette/glyph for each
  step — all without Qt and without RAW_DATA.
- The four edge cases each return a well-defined result the view can render
  (no exceptions escape the model).
- Palette/glyph output matches the design doc table exactly (verified by test).
