# KCWI/KCRM Datacube Coordinate-System Review

Branch context (as of this writing):

- Branch order for merging into `develop`: `develop` <- `kcwi_dec_2024` <- `kcwi_dec_2024_weights` <- `fix-cube-manual-coords-kbw`.
- Mapping to `PypeIt-development-suite` branches:
  - `PypeIt:kcwi_dec_2024` -> `PypeIt-development-suite:develop`
  - `PypeIt:kcwi_dec_2024_weights` -> `PypeIt-development-suite:kcwi_wcs`
  - `PypeIt:fix-cube-manual-coords-kbw` -> `PypeIt-development-suite:fix-cube-manual-coords-kbw`
- `PypeIt-development-suite:kcwi_wcs` and `PypeIt-development-suite:fix-cube-manual-coords-kbw` were identical at the time of writing. All further changes should occur in `PypeIt:fix-cube-manual-coords-kbw` and `PypeIt-development-suite:fix-cube-manual-coords-kbw`.

Primary sticking point for merging this series: confirming the coordinate system used when constructing KCWI/KCRM datacubes is correct, and that source detection/extraction within the cube use a coordinate convention consistent with the cube's WCS. Because of the FITS data-storage convention, the datacube array axis ordering is (wavelength, declination, right ascension), the opposite order of the WCS axes stored in the header. When displaying the "whitelight" image (cube collapsed along the spectral axis) with `matplotlib.pyplot.imshow` and the (0,0) pixel at the bottom-left, the image should be "sky-right": right ascension increasing towards the left, declination increasing upward (North up, East left).

This document was originally scoped to the cube-construction/WCS/extraction files (`pypeit/core/datacube.py`, `pypeit/coadd3d.py`). It has since been broadened to cover **all Python code differences** between the three branches (excluding everything under `doc/`), to catch coordinate-relevant or otherwise notable changes outside those two files.

## Summary of differences between the three branches

### 1. `develop` -> `kcwi_dec_2024` (the big rewrite)

21 python files changed (excluding `doc/`): `3085 insertions(+), 1027 deletions(-)`. This is where the array-axis-order vs. WCS-header-order convention (wavelength, dec, ra in the numpy array; ra, dec, wavelength in the WCS) was put in place, and where most of the new datacube-extraction machinery was introduced.

**Cube construction / WCS (`pypeit/core/datacube.py`, `pypeit/coadd3d.py`):**

- `create_wcs()` (datacube.py:2134): `voxedges` changed from `(xbins, ybins, spec_bins)` -> `(spec_bins, ybins, xbins)`, and the reference-image shape unpacking flipped from `numra, numdec = reference_image.shape` -> `numdec, numra = reference_image.shape`.
- `subpixellate()` (datacube.py:2892): the `wcs_world2pix(...)` result is now reversed on its last axis (`[:,:,::-1]`) before being histogrammed into `(wave, dec, ra)`-ordered bins.
- `align_user_offsets()` / `wcs_bounds()` / `subpixellate()`: the sign of the user-supplied RA/Dec offset flipped from `+=` to `-=` in three places, consistently.
- `generate_WCS()` (datacube.py:2247): `crpix = [numra, 0, 0]` combined with `cdelt = [-dspat, dspat, dwave]` -- this is the mechanism intended to produce "North up, East left" when displayed with `imshow`.
- `subpixellate()` was also reworked for performance: it now calls two new vectorized helpers added to `pypeit/utils.py`, `occurrences_sorted()` (a 2D generalization of the existing `occurrences()`, replacing a per-row `np.apply_along_axis` loop) and `linear_interpolate_extrapolate()` (replacing `scipy.interpolate.interp1d(..., fill_value='extrapolate')` for the RA/Dec-vs-spatial-position interpolation). Both were checked numerically against what they replaced (fuzz-tested against the old implementations) and found equivalent for the way they're actually called (`occurrences_sorted` does not actually require pre-sorted input despite its name; `linear_interpolate_extrapolate` requires an increasing `xp`, which both call sites already guarantee by sorting first).

**New alignment/extraction machinery (`pypeit/core/flexure.py`, `pypeit/manual_extract.py`, `pypeit/par/pypeitpar.py`, `pypeit/alignframe.py`, `pypeit/core/findobj_skymask.py`):**

- `core/flexure.py`: `calculate_image_phase()` gains a `force_cc=False` kwarg that, when `True`, short-circuits to the plain masked cross-correlation (`calculate_image_offset()`) instead of the skimage `phase_cross_correlation`/`optical_flow_tvl1` path. This backs a new `'cc'` multi-exposure alignment method, alongside the existing `'phase'` and `'fit'` methods, selected via the new `CubePar.alignment_method` parameter (see below) and wired up in `coadd3d.py`.
- `manual_extract.py`: new `ManualCubeExtractionObj(datamodel.DataContainer)` class. Parses a `x:y:fwhm:boxcar_radius`-style string (semicolon-separated for multiple objects) into `spatx`, `spaty`, `fwhm`, `boxcar_rad` fields (`spatx`/x always parsed first). This class and its field order were correct from this very first introduction -- the x/y bug fixed in the final branch (see section 3) was downstream of this parsing, not in it.
- `par/pypeitpar.py`: substantial growth to support the above: `AlignPar.grow_slit_edge` (default `0.0`); `CubePar.align` (bool) removed and replaced by `CubePar.alignment_method` (str, default `'phase'`, options `none/user/phase/cc/fit`); `CubePar.save_native` (bool, default `False`); `CubePar.weights_init_obj_pos` (str, `x:y` format, seeds `fitGaussian2D` for weight computation); `CubePar.sn_smooth_npix`; and a brand-new `CubeExtractionPar` sub-parset (`output_filename`, `whitelight_range`, `fwhm`, `snr_thresh`, `manual`, `boxcar_radius`, `opt_prof_method`, `skysub_resid`).
- `alignframe.py`: `TraceAlignment`'s slit-fitting loop now searches for alignment traces using edges grown by `grow_slit_edge` pixels (`left - grow_slit_edge` / `right + grow_slit_edge`), fixing failures when alignment traces sit right at a slit edge. `AlignmentSplines.build_splines()` also gained a `verbose=False` parameter, but it is never referenced in the function body (dead parameter, flagged below).
- `core/findobj_skymask.py`: a stray `debug_all = False` line inside `objs_in_slit()` that unconditionally shadowed the function's own `debug_all` keyword argument was removed -- this was silently disabling the debug-plotting path regardless of what callers passed; a genuine bug fix, landing in the same commit as the `alignframe.py` change above.
- New test coverage: `pypeit/tests/test_datacube.py` gained `make_point_source_image()` (builds a synthetic 2D-Gaussian point source from RA/Dec via a WCS) and three tests -- `test_align_phase`, `test_align_cc`, `test_align_fit` -- each simulating two point sources with a known RA/Dec offset and checking that the corresponding alignment method recovers it to within 1/3 pixel. This is the first real coordinate-correctness test coverage in the codebase for this workflow, and is a useful existing baseline for the test-writing effort proposed later in this document.

**Datacube axis ordering propagated to spectrograph classes (`pypeit/slittrace.py`, `pypeit/spectrographs/keck_kcwi.py`):**

- `slittrace.py`: `SlitTraceSet.get_radec_image()` (used by `subpixellate()` to build per-pixel RA/Dec images) renamed its `minmax` return value to `delta_pix` (both call sites updated) and gained a `verbose` kwarg. More significantly, its handling of a masked slit changed from a tolerant "log and skip this slit, continue with the rest of the image" to raising `PypeItError` for the entire call (flagged in the Inconsistencies section below).
- `spectrographs/keck_kcwi.py`: the per-slicer WCS pointing offsets (`off1`/`off2` for the large/medium/small slicer, e.g. `(1.0, 4.0)`, `(1.0, 5.0)`, `(0.05, 5.6)`) were restored from a temporary `off1 = off2 = 0.` stub -- these feed directly into `crpix`/absolute sky registration (flagged below). Separately, `get_datacube_bins()`'s return order was reversed from `(x, y, wave)` to `(wave, y, x)` to match the `create_wcs()`/`subpixellate()` axis-order rework above; a `# TODO :: Before merging note that this needs to be updated for all IFU spectrographs` comment was left in place, and indeed it was not (flagged below).

**CLI scripts kept in sync (`pypeit/scripts/coadd_2dspec.py`, `coadd_datacube.py`, `extract_datacube.py`):**

- `coadd_2dspec.py`: purely additive timing/logging (`utils.get_time_string`), no API change.
- `coadd_datacube.py`: adds `--debug`; updates the `CoAdd3D.get_instance(...)` call for the new `redux_path`/`debug` constructor arguments. A leftover unused `from pathlib import Path` and an unused `from IPython import embed`, plus a stale commented-out `output_paths(...)` call with an outdated signature, remain in the file (cleanup item, not a bug).
- `extract_datacube.py`: adds `--debug`; the CLI-provided `--save`/`--boxcar_radius` are now written into `par['reduce']['cube']['extraction'][...]` instead of being passed as separate keyword arguments, matching a corresponding signature change in `CoAdd3D.extract_spec()`; adds an `output_paths(...)` call to compute the science-directory path. A computed `qa_path` is never used, and a local `boxcar_radius = args.boxcar_radius` assignment is dead code (the real assignment happens a few lines later); a module-level `from IPython import embed` also breaks the file's otherwise-lazy import convention.

**Cosmetic-only changes** (mentioned for completeness, not elaborated): `core/wavecal/autoid.py` (a debug-plot y-limit hardcoded to `10.0` plus a commented-out original line, in `reidentify()` -- flagged as a minor cleanup item below); `display/display.py` (two docstring typo fixes); `core/extract.py` (one blank line); `tests/test_install.py` (whitespace only); `spectrographs/jwst_nirspec.py` (one unrelated line adding `allowed_extensions` for input-file discovery); `core/coadd.py` (an unrelated `wave_grid_input` passthrough feature added to `multi_combspec()`, plus a docstring update to `sn_weights()`).

### 2. `kcwi_dec_2024` -> `kcwi_dec_2024_weights`

5 python files changed: `207 insertions(+), 169 deletions(-)`. Mostly a structural refactor of `SlicerIFUCoAdd3D.run()` in `pypeit/coadd3d.py` (extracting a `make_datacubes()` method, adding `save_separate`), plus the root cause and fix of a real bug:

- `core/combine.py`: `weighted_combine()`'s signature changed from `weighted_combine(weights, sci_list, var_list, inmask_stack, ...)` to `weighted_combine(sci_list, var_list, inmask_stack, weights=None, ...)` -- `weights` moved from the first positional argument to a trailing keyword that defaults to uniform weighting when omitted. `broadcast_weights()` also gained support for 4D weight/shape arrays (`(nimgs, nspec, nspat1, nspat2)`) needed for cube stacking.
- This signature change is the confirmed root cause of the bug fixed in `coadd3d.py` in this same transition: `SlicerIFUCoAdd3D`'s call to `weighted_combine()` was still passing `weightcube_stack` **positionally** in the old first-argument slot, which after the signature change silently bound it to `sci_list` instead. The fix passes it as `weights=weightcube_stack`.
- `core/coadd.py` (`compute_coadd2d()`) and `images/combineimage.py` (two call sites) were correctly updated to the new `weighted_combine()` call convention in this same transition.
- `par/pypeitpar.py`: added `CubePar.save_separate` (bool, default `False`) -- write per-input spec3d cubes at the *final/combined* sampling, as a complement to `save_native`'s *native* sampling.
- `tests/test_datacube.py`: added `test_datacube_whitelight_range_datamodel`, a FITS round-trip / backward-compatibility test for the new `whitelight_range` datamodel field (see section 3) -- unrelated to spatial coordinates.

### 3. `kcwi_dec_2024_weights` -> `fix-cube-manual-coords-kbw` (current branch)

8 python files changed: `848 insertions(+), 122 deletions(-)`. This is the actual coordinate-convention fix that gives the branch its name, plus one new CLI script.

- `fitGaussian2D()` and `extract_point_source()` (datacube.py:778, datacube.py:1058) used an internal convention where the variables *named* `x`/`xobj` actually held the row (Dec/numpy-axis-0) index and `y`/`yobj` held the column (RA/numpy-axis-1) index -- the opposite of the Ginga/DS9 `(x,y)` convention stated in the docstrings. This mislabeling was self-consistent for the **DAOStarFinder/Gaussian-fit auto-detected** object position, because a final `yobj, xobj = gaussian_position` swap undid the internal mislabeling right before the value was used for masking/extraction. But it was **not** consistent for **user-supplied `manual_position`**: `yobj, xobj = manual_position` silently swapped the user's x and y.
  - Auto object-finding: happened to extract the right spaxel (by an internal double-swap), but logged `FWHM_x`/`FWHM_y` backwards, and passed `(yy, xx)` instead of `(xx, yy)` into `gaussian2D()` for `opt_prof_method='user_gauss'` (again a compensating swap, not a bug in effect).
  - **Manual position**: any user who set `manual="x:y:..."` per the documented Ginga/DS9 convention got the wrong spaxel extracted.
- The fix rewrites `fitGaussian2D`, `extract_point_source`, `whitelight_objfind_qa`, and `compute_weights_frompix` in `pypeit/core/datacube.py` to use one consistent `x=column(RA-axis)`, `y=row(Dec-axis)` convention throughout, and applies a companion fix in `SlicerIFUCoAdd3D` (coadd3d.py:1694), where the multi-exposure alignment code (`ra_pix_star, dec_pix_star = gaussian_position`) had the same swap. It also adds `DataCube.whitelight_range` (a new datamodel field, version bump `1.2.0`->`1.3.0`) so `pypeit_extract_datacube` can recover the default white-light wavelength range used during cube construction, and a couple of `PypeItError`s for slits with zero valid pixels (data-quality guards, not coordinate-related).
- `manual_extract.py` and `par/pypeitpar.py`: **documentation-only** changes rewording "spatx/spaty" to "x/y" and spelling out the Ginga/DS9 `image[y,x]` convention explicitly -- the underlying field order/parsing code is untouched, confirming it was already correct.
- New `pypeit/scripts/setup_datacube.py` (~429 lines, registered in `scripts/__init__.py`) and companion `pypeit/tests/test_setup_datacube.py` (~123 lines): a new `pypeit_setup_datacube` CLI script that stages point-source cube-extraction runs from an existing `run_pypeit` reduction. Given a pypeit file and a target name, it locates matching spec2d products and writes a `.coadd3d` config file (cube-construction parameters) and a companion `.extract` config file (extraction parameters, including an optional `manual` string), with `--append`/`-o/--overwrite` support for incremental updates. Its own `--manual` validation only accepts the 2-field `x:y` format (flagged below).
- `tests/test_datacube.py`: fixes a transposed RA/Dec assignment in `test_align_fit` itself (`dec_pix_star, ra_pix_star = gaussian_position` -> `ra_pix_star, dec_pix_star = gaussian_position`) -- this was a **test-only** bug; the corresponding production code in `coadd3d.py` already used the correct order from `kcwi_dec_2024_weights` onward, so this doesn't indicate a previously-passing regression test masked a real bug, just that the test itself needed the same fix applied to production code in section 3 above.

**Net effect of this branch**: for *auto* object finding, this branch reproduces the same extracted spaxel as `kcwi_dec_2024_weights` (the double-swap made that path accidentally correct) but with correct FWHM_x/FWHM_y reporting. For *manual* positions, this branch changes behavior -- it's the actual fix.

## Inconsistencies / questions for the team

1. **Is the auto-detection path really unchanged in effect?** Tracing through the algebra suggests the old (buggy) code's internal double-swap canceled out for the *position* used in extraction, but this has not been confirmed numerically. Worth confirming with a regression test that feeds an identical whitelight image into both the old and new `fitGaussian2D`/`extract_point_source` and checks the extracted spaxel indices and flux are bit-for-bit identical for the auto path, and *differ* (in the expected way) only for `manual_position`.
2. **Sign of `ra_shifts`/`dec_shifts` in the cross-correlation alignment** (coadd3d.py:1696) was not re-derived from scratch here -- it depends on both the `gaussian_position` convention fix and the `cdelt[0]=-dspat` sign convention from the `kcwi_dec_2024` rewrite. Since these two fixes landed in different branches, it's worth an explicit test that two exposures with a known, deliberately-offset synthetic point source recover the correct offset in the correct direction.
3. **The `develop -> kcwi_dec_2024` sign/axis-order changes were bundled together** (offset sign flip + `voxedges` reorder + `world2pix` axis reversal + `crpix` placement). Even though the dev suite passed, a unit-level test isolating just `generate_WCS`/`create_wcs` would help ensure a future edit to one of those four pieces can't silently break the others without a fast test catching it (dev-suite runs are expensive and end-to-end, so they wouldn't localize a regression here).
4. **`build_cube_common`/`project_to_sky`** (datacube.py:233, datacube.py:521) is a separate, newer cube-building code path for the `Fiber` pypeline (e.g., Binospec) that duplicates some of this logic independently (it builds its own `wcs.WCS(naxis=3)` with `cd`, not `cdelt`, and gets its RA/Dec convention from `spectrograph.ifu_sky_wcs()`). It's not used by KCWI/KCRM (those are `SlicerIFU`), but worth confirming with the team that it isn't meant to converge with `create_wcs`/`generate_WCS` -- right now they're independent implementations of the same "sky-right" intent.
5. **`get_datacube_bins()` axis order is now inconsistent across spectrographs.** `keck_kcwi.py`'s `get_datacube_bins()` was updated to return bins in `(wave, y, x)` order to match the reworked cube-axis convention in `datacube.py`, but `spectrographs/gemini_gnirs.py` and `spectrographs/gtc_osiris.py` (the other IFU spectrographs) still return the old `(x, y, wave)` order, and the base `Spectrograph.get_datacube_bins()` docstring was not updated either. A `# TODO :: Before merging note that this needs to be updated for all IFU spectrographs` comment was left in `keck_kcwi.py` but never actioned. Since `datacube.py` now globally assumes `bins[0]` is wavelength, GNIRS-IFU and GTC/OSIRIS datacube construction would silently cross spatial and spectral bins as things stand. **This should be resolved (fix those spectrographs' return order, update the base-class docstring, or confirm they are intentionally out of scope and file a follow-up) before merging into `develop`**, since it's a correctness regression for instruments outside this project's immediate scope.
6. **`weighted_combine()`'s `weights` parameter moved from positional to keyword** (`core/combine.py`, in `kcwi_dec_2024_weights`) -- this is the confirmed root cause of the `coadd3d.py` bug described in section 2 above. `core/coadd.py` and `images/combineimage.py` were updated correctly in the same transition, but it's worth a repository-wide grep for any other caller still passing `weights` positionally before merging, in case one was missed.
7. **`core/flexure.py` carries ~180 lines of duplicated, unreachable code.** `spec_flexure_corrQA()` and `spec_flexure_qa()` are pasted byte-for-byte into `flexure.py`, but these functions already live in (and are actively called from) `pypeit/qa.py`/`extraction.py`. This looks like merge fallout: a `develop` commit relocated these functions out of `flexure.py` into `qa.py`, and `kcwi_dec_2024` forked before that commit, with later "merge develop into kcwi_dec_2024" merges failing to propagate the deletion. The orphaned copies in `flexure.py` are missing required imports (`inspect`, `qa`) and would raise `NameError` if ever invoked. They should simply be deleted before merging to `develop`.
8. **`calculate_image_phase()`/`calculate_image_offset()` docstrings document the wrong return order.** Both document a return of `(ra_diff, dec_diff)`, but every call site (`coadd3d.py:1590`, `test_datacube.py`) unpacks the result as `dec_shift, ra_shift = ...`. The new `test_align_cc`/`test_align_phase` tests numerically validate that the current (swapped) behavior recovers injected offsets correctly, so the code is very likely right and the docstrings are simply stale -- but they should be corrected so a future maintainer doesn't "fix" the code to match the wrong docstring.
9. **`CubeExtractionPar.manual`'s documented format doesn't match its own validation.** The docstring documents a 4-field format (`x:y:fwhm:boxcar_radius`), but `CubeExtractionPar.validate()` raises `ValueError` unless each semicolon-separated entry has *exactly* 2 colon-separated fields -- unchanged across all three branches (only the error wording changed from "spatx/spaty" to "x/y" in the final branch). The new `pypeit_setup_datacube` script's own `--manual` validation independently enforces the same 2-field-only rule, so at least the new script and `validate()` agree with each other, but neither matches the documented 4-field format. **Needs a decision**: either loosen `validate()` (and the script's validation) to actually accept the documented `fwhm`/`boxcar_radius` fields, or fix the docstrings in `pypeitpar.py`, `manual_extract.py`, and `setup_datacube.py` to drop the unsupported fields.
10. **`SlitTraceSet.get_radec_image()` masked-slit handling became a hard failure.** Previously, a masked slit (e.g. from vignetting or a bad column) was logged and skipped, leaving the rest of the RA/Dec image populated; now it raises `PypeItError` and aborts the entire call, which in turn aborts datacube construction. Worth confirming this trade-off is intentional for KCWI/KCRM, where partial slit masking is not a rare occurrence -- a single bad slit would now turn a previously-successful (if degraded) reduction into a hard failure.
11. **`keck_kcwi.py`'s restored per-slicer pointing offsets** (`off1`/`off2` for the large/medium/small slicer, replacing a temporary `0.` stub) feed directly into `crpix` and hence absolute sky registration. Worth confirming these specific restored values are current/correct and asking whether KCRM needs its own values or is expected to inherit KCWI's.
12. **Minor cleanup items** noted during the broadened review, none affecting correctness but worth resolving before merge: an unused `verbose` parameter on `AlignmentSplines.build_splines()` (`alignframe.py`); a hardcoded debug-plot y-limit (`10.0`) and a commented-out original line left in `autoid.py`'s `reidentify()`; unused `Path`/`IPython.embed` imports and a stale commented-out `output_paths()` call (with an outdated signature) in `scripts/coadd_datacube.py`; an unused `qa_path` variable and a dead local `boxcar_radius` assignment in `scripts/extract_datacube.py`.
13. **`create_wcs()`'s pixel-count truncation can drop up to ~1 pixel of range at the extreme edge of the FOV.** `numra`/`numdec`/`numwav` are computed via `int(...)` (truncation) rather than rounding up, so when the true required pixel count has a large fractional part (e.g. 6.67), the resulting integer pixel grid can be up to a full pixel short of the true `[ra_min, ra_max]` (etc.) span. Since the grid's reference pixel (`crpix`) is anchored to one edge of the range, it is the *other* edge that can fall outside the nominal `[0, numra-1]` grid. For continuous, real illumination this only clips a negligible sliver of the faintest edge pixels -- but it was discovered here (while implementing the Phase 2 test below) with a synthetic three-slit field where one slit's *entire* flux sits at the extreme RA value: that slit's flux fell completely outside the pixel grid and was silently dropped by the histogram step, with no error or warning. Worth a decision: round up (`np.ceil`) instead of truncating, or otherwise pad the computed bounds by a fraction of a pixel, so the full data range is always covered.
14. **`fast_histogram.histogramdd` segfaults (an uncatchable process crash, not a Python exception) given NaN input.** Also discovered while implementing the Phase 2 test below: an idealized synthetic slit with perfectly straight, untilted edges produced exact duplicate values in the along-slit spatial-offset array that `subpixellate()` linearly interpolates over, causing a division-by-zero -> NaN that crashed the Python process inside `fast_histogram`'s C extension instead of raising a normal exception. Real slits always have some curvature/tilt, so this exact degenerate case is unlikely in practice -- but it means any code path that manages to feed a NaN into `subpixellate()`'s `vox_coord` (an unusual calibration, a zero-width slit, a bad astrometric fit) would crash the whole reduction ungracefully rather than failing with a diagnosable error. Worth considering an explicit finite-value check on `vox_coord` before the `histogramdd` call, raising a clear `PypeItError` if any non-finite values are found.
15. **`astropy.wcs.WCS` silently rewrites `.wcs.cdelt`/`.wcs.crval` for the wavelength axis, in place, the first time the WCS is evaluated.** Discovered while implementing the Phase 2a test below: a WCS built by `generate_WCS()` with `cunit=['deg','deg','Angstrom']` reads back its original, as-constructed `crval`/`cdelt` values correctly right after construction, but the moment it is used in any `wcs_world2pix`/`wcs_pix2world` call (e.g. inside `subpixellate()`), wcslib normalizes the wavelength axis to its canonical spectral unit (metres) and overwrites `.wcs.crval[2]`/`.wcs.cdelt[2]` in place -- e.g. a wavelength step of `78.17` (Angstrom) silently becomes `7.817e-09` (metres) if read back afterwards. The RA/Dec axes are unaffected (degrees is already wcslib's canonical angular unit). This isn't a bug in `datacube.py` today -- nothing in the current codebase reads back `cdelt`/`crval` from an already-used WCS object -- but it is a sharp edge for any future code (or test) that does, since re-feeding the read-back value into a *new* `generate_WCS()` call (which hard-codes `cunit=Angstrom`) produces a badly inconsistent WCS with no error or warning.
16. **`CubeExtractionPar.manual` silently dropped every object but the first in a semi-colon-separated multi-object string, with no error or warning.** Surfaced during the item 9 discussion: `CubeExtractionPar.validate()` only checked that *each* semi-colon-separated entry had exactly two colon-separated fields, so a string like `10:20;30:40` (two valid objects) passed validation cleanly. `ManualCubeExtractionObj.parse()` (`manual_extract.py`) then correctly parsed *both* objects into `spatx`/`spaty` arrays -- the semi-colon was not ignored at the parsing stage -- but both of `coadd3d.py`'s consumers of that parsed result (`manual_position = (spatx[0], spaty[0])` for `CubeExtractionPar.manual`, and the identical pattern for the separate, unvalidated `CubePar.weights_init_obj_pos`) hard-index element `[0]`, discarding everything else. The initial assumption that a semi-colon would fail anyway (via a downstream float-cast error) was checked and found incorrect: all the values cast to floats without error, so nothing catches this -- a user requesting extraction of multiple objects would silently get only the first, with no indication anything was dropped. Fixed for `CubeExtractionPar.manual` specifically (see below); the intended broader functionality (whether/how to eventually support multiple manually-extracted objects, and whether `weights_init_obj_pos` needs the same guard) requires broader team input and is left for a future PR.

## Proposed test plan (synthetic data, cheap first)

**Note on existing coverage**: the broadened review found that `pypeit/tests/test_datacube.py` already has `test_align_phase`, `test_align_cc`, and `test_align_fit`, which inject a synthetic point source with a known RA/Dec offset and confirm each alignment method recovers it to within 1/3 pixel. This is real, working coordinate-correctness coverage and should be used as a template/starting point rather than duplicated. There is, however, **no existing test** of `subpixellate()`'s core RA/Dec/wavelength -> voxel-index transform in isolation, nor of `AstrometricTransform`/manual-coordinate handling in `coadd3d.py` -- those remain gaps for the plan below to fill.

The key design constraint -- avoid reflective/rotational symmetry -- means every synthetic test source layout needs at least one feature that breaks all four of: horizontal flip, vertical flip, 180-degree rotation, and transpose (RA<->Dec swap). A single off-center point source is not enough (it's symmetric under a 180-degree rotation about itself combined with a translation of the whole frame); better to use **two or three point sources of different, unequal brightness at positions that form a scalene, chiral arrangement**, e.g. a right triangle with unequal legs and unequal fluxes, so no flip/rotation/transpose maps the pattern onto itself.

**Mapping to open questions**: this plan is written to directly close out open questions 1-3 from the "Inconsistencies / questions for the team" section above (items [Q1], [Q2], [Q3] below correspond to those three numbered items). Items 4 and onward in that section, including the important item 5 (the `get_datacube_bins()` axis-order mismatch across IFU spectrographs), are intended to be addressed later in this branch and are not yet covered by tests below.

### Phase 1a -- object-finding/extraction coordinate convention [Q1]

Directly tests whether the `fix-cube-manual-coords-kbw` fix changed the *auto-detection* extraction result (it shouldn't have) while fixing the *manual-position* result (it should have).

- Build a synthetic 2D "whitelight" image (say 15x20, non-square to catch axis-order bugs -- a square image can't distinguish `(ny,nx)` from `(nx,ny)`) with 2-3 asymmetric Gaussian point sources at known, unequal `(row, col)` positions and unequal fluxes.
- Feed it to `fitGaussian2D()` directly and assert the returned position matches the known column (x) and row (y) index of the brightest source, i.e. verify `xobj` tracks the array's fast/last axis and `yobj` tracks the slow/first axis. Add a `gpm`/edge-mask case to make sure masking doesn't accidentally transpose.
- Feed the same image with `manual_position` set to the (correct) `(x,y)` of a fainter source and confirm `fitGaussian2D`/`extract_point_source` lock onto that source, not the brightest one -- this is the direct regression test for the bug this branch fixes.
- **Non-regression check against the pre-fix behavior**: encode the *old* (`kcwi_dec_2024_weights`) position-unpacking logic as a short, self-contained reference implementation directly in the test file (a few lines reproducing the old `yobj, xobj = ...` swap and the old `indexing='ij'` meshgrid setup, not a live import from an old commit, so the test doesn't depend on old branches/commits remaining available). Run both the old reference logic and the current `pypeit.core.datacube.fitGaussian2D`/`extract_point_source` on the same synthetic multi-source image and assert:
  - For **auto-detection** (`manual_position=None`), the extracted spaxel index and optimally-extracted flux are identical (to floating-point tolerance) between the old and new code -- this directly confirms or refutes the suspicion (noted in [Q1]) that the double-swap in the old code canceled out for the auto path.
  - For a **manual position** supplied in the documented Ginga/DS9 `(x,y)` convention, the new code extracts the correct known source while the old reference logic extracts the wrong (transposed) spaxel -- this demonstrates and locks in the actual bug fix as a permanent regression test.

### Phase 1b -- decomposing the bundled WCS axis-order/sign changes [Q3]

The `develop -> kcwi_dec_2024` rewrite bundled four separate coordinate-convention changes into one large commit (RA/Dec offset sign flip, `voxedges` axis reorder, `wcs_world2pix` output-axis reversal, and the `crpix`/`cdelt` sky-right placement in `generate_WCS`). The dev suite validated the combination, but no fast test protects any one piece in isolation. Add four small, independent unit tests, each able to fail on its own without needing a full cube build:

- **Offset-sign test**: call `wcs_bounds()` with a synthetic `raImg`/`decImg` and a nonzero `ra_offsets`/`dec_offsets`, and confirm the offset is *subtracted* from the pixel RA/Dec (per the `+=` -> `-=` change), not added.
- **`voxedges` order test**: call `create_wcs()` with deliberately *different* numbers of RA bins, Dec bins, and wavelength bins (so a silent axis swap can't hide behind equal-length arrays) and assert the returned `voxedges` tuple is ordered `(spec_bins, ybins, xbins)`.
- **Sky-right `crpix`/`cdelt` test**: call `generate_WCS()` directly with known, asymmetric `crval`/`cdelt` inputs and assert `wcs_pix2world` recovers RA *decreasing* as pixel-x index increases (the "sky-right" condition), independent of `create_wcs`/`subpixellate`.
- **`world2pix` axis-reversal test**: exercise the `output_wcs.wcs_world2pix(...)[:,:,::-1]` step inside `subpixellate()` with a minimal single-slit, single-subpixel synthetic call (no need for the full multi-slit/multi-subpixel machinery), and assert the reversed voxel-coordinate order matches `(wave, dec, ra)` before it is histogrammed. This is the piece most likely to silently regress in isolation, since nothing else currently exercises the reversal directly.

### Phase 2 -- synthetic cube through `subpixellate`/`generate_cube_subpixel` (still cheap, skips real calibration/extraction)

- Construct a minimal synthetic `sciImg`/`ivarImg`/`waveImg`/`slitid_img_gpm`/WCS/tilts/slits representing 2-3 narrow "slits" with a couple of point sources at asymmetric positions (again non-square, chiral layout), run it through `generate_cube_subpixel`, and check that the resulting cube's brightest voxel (collapsed to a whitelight image) sits at the pixel whose *sky coordinates* (via the cube's own WCS) match the input synthetic RA/Dec, not merely that "some pixel is bright."
- Add a second synthetic frame with a known RA/Dec offset (via `ra_offsets`/`dec_offsets`) and confirm the combined cube registers the two frames correctly -- this tests the offset-sign convention from `kcwi_dec_2024` end-to-end without needing real calibrations.

### Phase 2a -- cross-correlation alignment sign convention [Q2]

The `ra_pix_star`/`dec_pix_star` unpacking fix (this branch) and the `cdelt[0] = -dspat` sky-right convention (`kcwi_dec_2024`) were introduced in different branches and have never been jointly unit-tested, even though the `ra_shifts`/`dec_shifts` formula in `SlicerIFUCoAdd3D` depends on both being correct together.

- Extend the existing `DAOStarFinder`->cross-correlation alignment test (`test_align_fit`/`test_align_phase`/`test_align_cc`, or a new sibling test) to build its WCS using the real `create_wcs()`/`generate_WCS()` (not an ad hoc test WCS), so the test exercises the actual `-dspat` sign convention alongside the `ra_pix_star`/`dec_pix_star` fix.
- Use an **asymmetric injected shift** between two synthetic exposures (different magnitude in RA than in Dec, e.g. 0.3" in RA and 0.7" in Dec) so a residual RA/Dec swap or sign error cannot cancel out or hide behind a symmetric shift.
- Assert the recovered `ra_shifts`/`dec_shifts` match the injected offsets in both sign and magnitude, independently for each axis.
- **Sensitivity check**: rerun the same test with the sign of `cdelt[0]` deliberately flipped (simulating a regression in `generate_WCS()`) and confirm the recovered shift's sign flips accordingly. This proves the test actually exercises the convention it's meant to protect, rather than passing tautologically regardless of the sign convention.

### Phase 3 -- imshow/orientation sanity check (matplotlib, still synthetic)

- Take the Phase-2 synthetic cube, collapse to whitelight, `imshow` with `origin='lower'`, and programmatically assert (not just visually) that the pixel corresponding to the higher-RA source appears at a smaller column index than the pixel for the lower-RA source (i.e., RA increases right-to-left = sky-right), and that Dec increases with row index (North up). This turns the "does it look sky-right" question into an assertion that can run in CI.

### Phase 4 (deferred to the dev suite, real data)

- Once phases 1-3 pass, add a dev-suite test using a real KCWI/KCRM standard-star or twilight-flat exposure with a known, catalogued companion or asymmetric feature (e.g., a binary star or a field with a known bright/faint pair) to confirm the same orientation and manual-position behavior survives real calibration, DAR correction, and multi-exposure combination -- this is the expensive end-to-end check and should only be added after the fast tests above are solid, given the cost of full cube construction.

## Test plan implementation

This section tracks the implementation of the test plan above, phase by phase, and records how each addressed item from the "Inconsistencies / questions for the team" section was resolved (where relevant to that phase).

### Phase 1a -- object-finding/extraction coordinate convention [Q1]

Implemented in `pypeit/tests/test_datacube.py` (all in `PypeIt`, no dev-suite changes needed since these are pure-numpy unit tests). Four new tests, all built around a single synthetic, non-square, two-point-source image (a bright and a fainter source at distinct, non-mirrored row/column positions, so no flip/rotation/transpose can accidentally satisfy the assertions):

- `test_fitgaussian2d_ginga_xy_convention`: confirms `fitGaussian2D()` (a) auto-detects the *brighter* source and reports its position as `(x, y) = (column, row)`, and (b) honors a manually-supplied `(x, y)` position by locking the fit onto the *fainter* source at that position instead.
- `test_fitgaussian2d_autodetect_unaffected_by_bugfix` / `_pre_fix_auto_position`: reproduces the pre-fix (`kcwi_dec_2024_weights`) DAOStarFinder + Gaussian-fit auto-detection logic bug-for-bug as a frozen reference implementation, runs it alongside the current `fitGaussian2D()` on the same image, and asserts the two agree to `1e-4` pixel on the final auto-detected position.
- `test_manual_position_bugfix_regression` / `_pre_fix_manual_position`: isolates the exact one-line bug (`yobj, xobj = manual_position` vs. the corrected `xobj, yobj = manual_position`) and asserts the pre-fix reference gives the transposed (wrong) answer while the current code gives the correct one.
- `test_extract_point_source_manual_position_selects_correct_source`: an integration-level test of the full `extract_point_source()` pipeline (not just `fitGaussian2D`) using a minimal synthetic 3D cube (`flxcube`/`ivarcube`/`bpmcube`/`wcscube`). Confirms that auto-detection (no `manual_position`) extracts the bright source's flux, while a manual position at the faint source's coordinates extracts a flux consistent with its lower amplitude instead -- closing the coverage gap noted earlier ("no existing test of ... `extract_point_source` itself").

**Resolution of [Q1]** ("Is the auto-detection path really unchanged in effect?"): **Confirmed, empirically.** `test_fitgaussian2d_autodetect_unaffected_by_bugfix` shows the pre-fix and post-fix code agree on the auto-detected position to `1e-4` pixel -- the internal double-swap in the pre-fix code did cancel out for the auto-detection path, as suspected. The manual-position path, by contrast, is demonstrably different before and after the fix (`test_manual_position_bugfix_regression`), and the fixed code now extracts the correct, requested source end-to-end (`test_extract_point_source_manual_position_selects_correct_source`). This item is resolved; no further action needed.

**A note on the two pre-fix reference helpers** (`_pre_fix_auto_position`, `_pre_fix_manual_position`) and the two tests that use them (`test_fitgaussian2d_autodetect_unaffected_by_bugfix`, `test_manual_position_bugfix_regression`): these intentionally duplicate old, buggy code as a frozen comparison point, and are marked in the test file as **temporary, branch-specific scaffolding** to be removed or refactored (e.g. folded into `test_fitgaussian2d_ginga_xy_convention` as ordinary, non-comparative assertions) before this branch stack is merged into `develop`. Once merged, there is no further value in re-deriving the pre-fix behavior, and carrying duplicated buggy code forward in the permanent test suite is a maintenance liability rather than an asset.

All 4 new tests pass, alongside the 10 pre-existing tests in `test_datacube.py` (14/14 passed locally, `pytest pypeit/tests/test_datacube.py`).

### Phase 1b -- decomposing the bundled WCS axis-order/sign changes [Q3]

Implemented in `pypeit/tests/test_datacube.py`, as four small, independent unit tests, each targeting exactly one of the four changes that were bundled into the `develop -> kcwi_dec_2024` rewrite:

- `test_wcs_bounds_subtracts_offsets`: calls `wcs_bounds()` directly with a nonzero, asymmetric `ra_offsets`/`dec_offsets` and asserts the returned RA/Dec bounds equal `image.min()/max() - offset`, not `+ offset`. Wavelength bounds are also checked to confirm they're unaffected by the RA/Dec offsets.
- `test_create_wcs_voxedges_axis_order`: calls `create_wcs()` with all six bounds (`ra_min/max`, `dec_min/max`, `wave_min/max`) specified explicitly -- chosen with deliberately different RA/Dec/wavelength spans so the resulting bin counts are distinct (10 RA bins, 6 Dec bins, 4 wavelength bins) -- and asserts `voxedges` unpacks as `(spec_bins, ybins, xbins)` with exactly those counts, so a silent axis reorder can't hide behind equal-length arrays. Bypassing image-derived bounds this way avoids needing any real `raImg`/`decImg`/`waveImg` data.
- `test_generate_wcs_sky_right_convention`: calls `generate_WCS()` directly with a known `crval`/`cdelt`/`numra` and asserts `wcs_pix2world` recovers strictly *decreasing* RA as the pixel-x index increases -- the direct definition of "sky-right" -- independent of `create_wcs`/`subpixellate`.
- `test_subpixellate_world2pix_axis_reversal`: rather than driving the full `subpixellate()` function (which requires mocking a `SlitTraceSet`, `AlignmentSplines`, tilts, and a `DARcorrection` object -- machinery that belongs to Phase 2, not this decomposition), this test reproduces the exact expression used inside `subpixellate()` (`output_wcs.wcs_world2pix(...).reshape(...)[:, :, ::-1]`) directly against a real WCS from `generate_WCS()`. It picks a target voxel index `(iwave, idec, ira)` with `iwave != ira`, computes the corresponding world coordinates via `wcs_pix2world` (WCS/FITS pixel order is `(ra, dec, wave)`), round-trips them back through `wcs_world2pix`, applies the same `[:, :, ::-1]` reversal, and asserts the result reproduces the original `(iwave, idec, ira)` -- i.e., that the reversal correctly reorders `wcs_world2pix`'s natural `(ra_pix, dec_pix, wave_pix)` output into the `(wave_pix, dec_pix, ra_pix)` order the cube's `(nwave, ndec, nra)` numpy array needs for histogramming. Choosing `ira != iwave` guarantees a missed or partial reversal would be caught.

**Resolution of [Q3]** ("The `develop -> kcwi_dec_2024` sign/axis-order changes were bundled together"): **Addressed.** Each of the four bundled changes (offset sign, `voxedges` order, sky-right `crpix`/`cdelt`, and the `world2pix` axis reversal) now has its own fast, independent regression test that does not depend on the others being correct. A future edit to any one of `wcs_bounds()`, `create_wcs()`, `generate_WCS()`, or the reversal line in `subpixellate()` will now be caught by a unit test in seconds, rather than only being detectable (if at all) by a full, expensive dev-suite run. This item is resolved; no further action needed beyond keeping these tests passing.

All 4 new tests pass, alongside the 14 tests from Phase 1a and the pre-existing suite (18/18 passed locally, `pytest pypeit/tests/test_datacube.py`).

### Phase 2 -- synthetic cube through `subpixellate`/`generate_cube_subpixel`

Both bullets of Phase 2 are now implemented: a single synthetic exposure through the full pipeline, and combining a second, offset exposure. Phase 2a (cross-correlation alignment sign convention, [Q2]) remains for follow-up work, per the earlier "hold off on Phase 2a for now" direction.

The two tests below share one synthetic 3-slit detector geometry, factored into two small helpers to avoid duplicating ~80 lines of setup between them: `_make_synthetic_three_slit_detector()` (builds the `SlitTraceSet`, tilts, `AlignmentSplines`, and a two-point-source science image) and `_make_synthetic_frame_wcs(ra0, dec0, wave0, dwv)` (builds a minimal per-exposure "instrument" WCS with a given celestial reference point, no rotation).

**Part 1 -- single exposure.** Implemented as `test_generate_cube_subpixel_recovers_injected_source_position` in `pypeit/tests/test_datacube.py`. This is the first test in the suite that drives the full `subpixellate()`/`generate_cube_subpixel()` pipeline end-to-end (rather than testing its pieces in isolation, as in Phase 1b), so it required building minimal-but-real instances of the supporting classes `subpixellate()` depends on:

- A `SlitTraceSet` with 3 narrow, straight slits (with a small per-row edge drift -- see below) on a 40x40-pixel synthetic detector.
- An `AlignmentSplines` built from the same slit traces, providing the detector-to-along-slit-offset transform.
- A minimal per-exposure "instrument" WCS (`astropy.wcs.WCS`, 3 axes: slit index, along-slit offset, spectral row -> RA, Dec, wavelength), built the same way `Spectrograph.get_wcs()` builds the real one, but with no rotation (diagonal CD matrix) for simplicity.

Two point sources of unequal brightness (amplitude 1.0 and 0.4) were injected at different slits *and* different spectral rows, so no flip/rotation of the field of view maps one onto the other. The "ground truth" sky position of each injected pixel is computed via `SlitTraceSet.get_radec_image()` using the *same* per-exposure WCS/astrometric-transform/tilts the cube is built from -- i.e., the test reuses the pipeline's own oracle rather than hand-deriving expected coordinates, which would risk transcription errors independent of the code being tested. The output cube is then built via `create_wcs()` + `generate_cube_subpixel()` (nearest-grid-point sampling, no DAR, since only whole-pixel positional correctness is being checked), and the test asserts that (a) the cube's single brightest voxel lands, via the cube's own WCS, at the bright source's true RA/Dec, and (b) the fainter source, in a different slit, is found at its true position with roughly the expected relative flux -- guarding against an axis mapping that happens to work only for the brighter source.

**Debugging notes** (kept here because they surfaced two genuine, previously-unknown issues, now added to the Inconsistencies list as items 13 and 14): getting this test to pass required three iterations beyond the initial design, each of which taught something about `subpixellate()`'s real behavior rather than being a mistake in the test's premise:

1. The synthetic on-slit mask must be derived from `SlitTraceSet.slit_img()` itself (`slitid_img_gpm = slits.slit_img(pad=0)`), not from the nominal `(left, right)` column bounds -- `slit_img()` uses strict inequalities and excludes the boundary columns, and a mask that disagrees with it includes detector pixels whose RA/Dec were never populated by `get_radec_image()` (left at 0.0), which corrupts `wcs_bounds()`'s min/max calculation.
2. Perfectly straight, untilted slit edges make the along-slit spatial offset from `AlignmentSplines.transform()` exactly degenerate between spectral rows, which crashes `fast_histogram` (item 14). A tiny per-row edge drift (a fraction of a pixel over the full spectral range) fixes this without introducing enough row/Dec coupling to disturb the position check. Similarly, tilts with zero column-dependence produce duplicate values in a different internal spline and trigger a (harmless, but avoidable) divide-by-zero warning; a similarly tiny per-column term in the tilts removes it.
3. The default, auto-derived `ra_min`/`ra_max`/`dec_min`/`dec_max` bounds passed to `create_wcs()` must be padded by a few output pixels beyond the true data extent, to avoid the truncation issue in item 13 -- without padding, the slit sitting exactly at the extreme edge of the RA range lost its flux entirely.

**Part 2 -- combining a second, offset exposure.** Implemented as `test_generate_cube_subpixel_combines_offset_frames_correctly`. Frame 1 and frame 2 share identical detector data (same `sciImg`, slits, tilts, `AlignmentSplines`) -- only their per-exposure WCS `crval` differ, by a deliberately asymmetric amount (different in RA than in Dec, e.g. 0.6" in RA and -0.9" in Dec). As discussed below ("A note on dither realism"), this deliberately does **not** model a physical telescope dither (which would move the object to different detector pixels); it models a *registration/astrometric discrepancy* between two exposures of the same, unmoved field -- e.g. guiding jitter or a timing error not fully captured in the header WCS -- of the kind a preceding alignment step (`SlicerIFUCoAdd3D.run_align()`) measures and hands off as `ra_offset`/`dec_offset`. The "true" per-frame registration offset here is derived from `SlitTraceSet.get_radec_image()` applied to each frame's own WCS at the bright source's pixel -- the same oracle used in Part 1 -- rather than hand-derived from the WCS's TAN-projection algebra. `wcs_bounds()`, `create_wcs()`, and `generate_cube_subpixel()` are all called with 2-element lists (`raImg`, `sciImg`, `all_wcs`, `astrom_trans`, `all_dar`, `ra_offset`/`dec_offset`, etc.), exercising the multi-frame combination path in `subpixellate()` for the first time in the test suite.

The test asserts, with the offset supplied with the correct sign (`ra_offset`/`dec_offset` subtracted, per the `kcwi_dec_2024` `+=` -> `-=` convention): (a) the combined cube's single brightest voxel is the bright source at frame 1's true (reference) position, (b) the faint source recovers its expected relative flux there too, and (c) no spurious source-level flux appears at the position frame 2's bright source would have landed at *had* the offset been applied with the wrong sign. A **sensitivity check** then rebuilds the cube with the offset's sign flipped (doubling frame 2's mis-registration instead of removing it) and confirms a distinct, source-level flux peak now appears at that wrong-sign position instead -- proving the checks above are actually sensitive to the offset's sign, not passing regardless of it (the same "prove the test isn't tautological" pattern planned for Phase 2a's sign-flip check).

One implementation pitfall worth recording: an earlier version of this test checked `normcube` (the per-voxel contributing-pixel count) directly at the expected source positions, expecting it to jump from ~1 to ~2 when both frames co-register. This failed with values like 39 (the full spectral length), because `normcube` accumulates *every* on-slit detector pixel weighted by `wghtImg` (uniform 1.0 across the whole slit here), not just pixels near the injected point source -- it is an occupancy count for the whole slit, not a per-source flux indicator. The fix was to check `flxcube` (actual flux, which is already normalized by occupancy) at specific sky positions instead, which is what the assertions above do.

**Part 3 -- a genuinely dithered pair of exposures, combined with zero offset.** Implemented as `test_generate_cube_subpixel_combines_genuine_dither_with_zero_offset`, added after a discussion (recorded below, "A note on dither realism") about what Part 2 does and does not validate. Here, a single point source is injected at *different* detector pixels in the two frames -- slit 0 in frame 1, slit 1 in frame 2, at the same along-slit offset and spectral row -- modeling a one-slice telescope dither. Frame 2's WCS `crval` is shifted by exactly one slice width (`SYNTH_SLICE_SCALE_DEG`, now a module-level constant shared with `_make_synthetic_frame_wcs`), matching the shift an *accurate* pointing-to-WCS translation would produce for a dither of that size. `ra_offset`/`dec_offset` are left at zero throughout: the test relies entirely on each frame's own WCS being self-consistent with where the object actually landed.

The test first confirms (numerically, not by assuming the algebra) that both frames' own `get_radec_image()` agree on the object's true sky position, then confirms the combined cube's single brightest voxel is that shared position -- i.e., the two, genuinely different flux distributions co-register correctly with no manual correction. A **sensitivity check** applies the same one-slice shift with the wrong sign (modeling, e.g., a sign error in `keck_kcwi.py`'s per-slicer `off1`/`off2` values -- Inconsistencies item 11) and confirms the two frames' flux now lands at two distinct, separated positions instead of co-registering -- demonstrating this test would catch that class of bug, which Part 2 cannot (Part 2 never varies which slit the object is in).

**Resolution note**: Phase 2 does not map to one of the three specific open questions [Q1]-[Q3] the way Phases 1a/1b do (that mapping is Phase 2a's [Q2]), but all three parts add fast, direct regression coverage for the bundled `develop -> kcwi_dec_2024` rewrite's end-to-end behavior -- Part 1 exercises the full `create_wcs`/`generate_WCS`/`subpixellate` chain together (rather than each piece in isolation, as Phase 1b does); Part 2 exercises the `ra_offset`/`dec_offset` sign convention (item 3's offset-sign piece, and the general subject of [Q2]) specifically inside the multi-frame combination path; and Part 3 exercises the (previously untested) claim that a genuinely dithered pair of exposures, with self-consistent per-exposure WCS, registers correctly on its own.

All 23 tests in the file pass with no warnings (beyond two pre-existing, unrelated warnings from `test_align_cc` and an astropy-plugin deprecation notice) (`pytest pypeit/tests/test_datacube.py`).

### A note on dither realism, and what these tests do and don't validate

After Phase 2a and Phase 3 were implemented, a discussion with the team lead flagged a concern about Parts 1-2 above (and, by the same construction, Phase 2a's test): the tests' docstrings described a shared-`sciImg`/different-`crval` construction as modeling things like "a deliberate dither," but a real dither should never leave the detector flux distribution unchanged -- moving the telescope moves where the light lands. This section records that discussion and how the tests were adjusted in response.

There are two distinct physical mechanisms that can produce a "registration discrepancy" between two exposures, and they call for different synthetic-test constructions:

1. **A real dither.** The telescope is deliberately (or accidentally, via guiding drift) pointed somewhere new, so the object's flux genuinely moves to different detector pixels, possibly a different slit entirely. If the astrometric solution is accurate, each exposure's own `frame_wcs`, built independently from its own header pointing information, should recover the *same* true sky RA/Dec for the object despite the different pixels -- no manual correction should be needed to combine them.
2. **An astrometric/registration error.** The telescope may not have moved at all (or moved by an amount already reflected in the header), but the *derived* WCS is imprecise -- guiding jitter not captured in the header, a timing error affecting the parallactic-angle calculation, an uncertain per-slicer offset, etc. Here the flux position is essentially unchanged, but the WCS's claim about where that flux sits on the sky is wrong by some small residual amount. This is exactly what `SlicerIFUCoAdd3D.run_align()`'s cross-correlation machinery is for: measuring and correcting that residual via `ra_offset`/`dec_offset`.

Before this discussion, every multi-frame test (Part 2 above, and Phase 2a) modeled mechanism 2 only (identical `sciImg`, varying `frame_wcs`), which is a reasonable and realistic model for `run_align()`'s actual, everyday job -- correcting small residual pointing/astrometric errors between repeat exposures of the same field -- but is not a physical model of a dither, and was described as one in places. None of the tests validated mechanism 1: that a *genuinely* different flux distribution, combined with a *correspondingly, consistently updated* per-exposure WCS, registers correctly using zero manual offset. That gap mattered because it's arguably the more fundamental claim for the multi-frame cube-building use case -- and it's specifically where a bug in KCWI's per-slicer `off1`/`off2` offsets (item 11) or in the slit-index-to-sky-position mapping would surface, since that bug would only manifest when the object actually moves between slits.

In response, two changes were made:
- The Part 2 docstring and test comments were corrected to describe the scenario accurately (a registration/astrometric discrepancy between an otherwise-unmoved field, not a dither), with an explicit pointer to Part 3 for the dither case.
- Part 3 (above) was added to close the gap: a genuinely different flux distribution per frame (different slit), a `frame_wcs` shift computed the way an accurate pointing-to-WCS translation would produce it, and a check that zero-offset combination registers correctly -- plus a sensitivity check that a wrong-sign per-slicer shift breaks that registration, which is what an `off1`/`off2` bug would look like.

Phase 2a's test was left as-is (same "flux fixed, WCS varies" construction) since, as explained above, that pairing is a reasonably faithful model of `run_align()`'s real use case rather than of a dither, and its docstring did not claim otherwise.

One important caveat, per the discussion: the team lead noted they don't have complete certainty about how the real pipeline is meant to work in practice (e.g., whether datacube WCS construction is purely notional from the recorded pointing/rotation, and whether coadding performs its own registration-based WCS adjustment for the combined cube) and plans to confirm with colleagues more familiar with this part of the code. Part 3's "accurate pointing-to-WCS translation" model should be treated as a reasonable working assumption for testing purposes, not a confirmed description of the production code's intended design -- it may need revisiting once that's confirmed.

### Phase 2a -- cross-correlation alignment sign convention [Q2]

Implemented as `test_align_phase_offset_sign_convention_via_real_wcs_pipeline` in `pypeit/tests/test_datacube.py`. Unlike `test_align_phase`/`test_align_cc`/`test_align_fit` (which build their own ad hoc 2D WCS), this test builds the white-light image WCS via the **real** `create_wcs()`/`generate_WCS()` pipeline, so it jointly exercises the actual `cdelt[0]=-dspat` sky-right convention (`kcwi_dec_2024`) together with `SlicerIFUCoAdd3D.run_align()`'s pixel-shift -> RA/Dec-offset conversion, exactly as they are coupled in production.

Frame 1 and frame 2 share identical detector data and slit/tilt/alignment geometry (reusing the Phase 2 helpers); only their per-exposure WCS `crval` differ by a known, asymmetric RA/Dec amount (0.3" in RA, -0.7" in Dec). The white-light image WCS/bins are built with `create_wcs(..., collapse=True)`, and per-frame white-light images with `generate_image_subpixel()` (no offset correction applied, mirroring `run_align()`'s state before an offset has been found). A single pass of `calculate_image_phase()` -- mirroring `run_align()`'s `'phase'` branch line-for-line, including its `ra_shift *= -dspat/cosdec` conversion -- recovers the offset, which is compared against the "true" offset measured via `SlitTraceSet.get_radec_image()` (the same oracle used throughout Phase 2).

**Sensitivity check**: a "regressed" WCS is built via `generate_WCS()` with `cdelt[0]` sign flipped (and `crpix` correspondingly re-anchored, exactly as the two are paired in `generate_WCS()`, so the same data still falls within the valid pixel range rather than being silently clipped entirely -- see the debugging note below). Rerunning the identical alignment procedure against this regressed WCS confirms the recovered RA offset's sign flips, while the (unrelated) Dec-axis recovery is unaffected -- proving the test is actually sensitive to the sky-right convention it's meant to protect, not passing regardless of it.

**Resolution of [Q2]** ("Sign of `ra_shifts`/`dec_shifts` in the cross-correlation alignment"): **Addressed.** The recovered offset matches the true injected registration difference in both sign and magnitude on both axes (to within 1/3 of the synthetic detector's along-slit pixel scale), using the real `create_wcs`/`generate_WCS` pipeline rather than an ad hoc test WCS, and the sign-flip sensitivity check confirms this result is genuinely coupled to the `cdelt[0]=-dspat` convention rather than incidental. This closes out the last of the three open questions the test plan was scoped to address ([Q1], [Q2], [Q3]).

**Debugging notes** (kept here because they surfaced one more genuine, previously-unknown issue, now recorded as item 15 in the Inconsistencies section, and one implementation pitfall specific to this test):

1. `astropy.wcs.WCS` silently normalizes a WCS's wavelength-axis `cdelt`/`crval` to metres (wcslib's canonical spectral unit) in place, the first time the WCS is evaluated via `wcs_world2pix`/`wcs_pix2world`. An initial version of this test read `image_wcs.wcs.crval`/`cdelt` to build the "regressed" WCS *after* first using `image_wcs` to recover the correct-sign offset -- by then, the wavelength axis's `cdelt`/`crval` had already been silently rewritten from Angstrom-scale to metre-scale values, and feeding that metre-scale value back into `generate_WCS()` (which hard-codes `cunit=Angstrom`) produced a badly inconsistent WCS whose white-light images came out entirely empty (all flux fell outside the valid wavelength bin), making the recovered offset trivially `0.0` for both frames. The fix was to extract `crval`/`cdelt` and build the regressed WCS immediately after `create_wcs()`, before `image_wcs` is ever evaluated.
2. Naively flipping only `cdelt[0]`'s sign (keeping `crpix`/`crval` unchanged) moves the *entire* data range outside the valid `[0, numra-1]` pixel bins -- `crpix=numra` is specifically paired with `cdelt[0]=-dspat` in `generate_WCS()` to keep `ra_min`/`ra_max` anchored within range for that sign; flipping the sign alone (not `crpix`) silently drops all flux, again giving a trivial, uninformative `0.0` result. The fix re-derives the regressed WCS via `generate_WCS(coord_min, [-cdelt[0], cdelt[1], cdelt[2]], numra=0)`, which correctly re-anchors `crpix` for the flipped sign (mirroring how `kcwi_dec_2024` originally paired the two).

### Item 5 -- `get_datacube_bins()` axis order across spectrographs

**Assessment (before fixing).** Before making any change, this item was investigated in detail to confirm it was a real, shared-code-driven bug rather than a cosmetic consistency-only issue (the team lead's specific concern going in):

- `get_datacube_bins()` has exactly one functional call site in the non-test codebase: `SlicerIFUCoAdd3D.save_native()` (`coadd3d.py:1730`), which feeds its return value directly into `datacube.generate_cube_subpixel()`. `save_native` defaults to `False` (`pypeitpar.py`) -- an opt-in feature that writes each input exposure at its own native sampling, separate from the main combined-cube product. The **default/main combined-cube path** (`make_datacubes()`) never calls `get_datacube_bins()` at all; it builds its own bins via `create_wcs()`. So this can only ever affect the native-sampling output, for two specific instruments, never the primary science-cube product for any instrument.
- The axis order is functionally load-bearing, not documentation-only: `subpixellate()` always treats `bins[0]` as the wavelength axis (`outshape = (bins[0].size-1, ...)`), while the per-pixel voxel coordinates it bins against are independently, always ordered `(wave_pix, dec_pix, ra_pix)`. Feeding it `bins` in `(x, y, wave)` order (as GNIRS-IFU and GTC/MAAT did) mismatches the histogram range against the actual data, and -- since the RA/slice-index range (order ~20) is vastly narrower than the wavelength-pixel range (order 1000+) -- would cause `histogramdd` to silently drop nearly all the flux, producing an obviously wrong-shaped, near-empty cube (verified numerically; see below).
- Checked directly against git history: current `develop` (which `kcwi_dec_2024` branched from and has not yet been merged back into) still has `create_wcs()` returning bins in the *old* `(x, y, wave)` order, exactly matching what GNIRS-IFU/GTC-MAAT's `get_datacube_bins()` still return. The new `(wave, y, x)` convention was introduced specifically by the `kcwi_dec_2024` rewrite (the same `voxedges` reorder documented in section 1 of this file), and only `keck_kcwi.py`'s copy was updated to match, with the `# TODO :: Before merging note that this needs to be updated for all IFU spectrographs.` comment left behind and never actioned. **Conclusion: this branch chain, unmodified, would introduce a new regression into `develop`** for two instruments that are correct today -- this is not a pre-existing issue and not merely a style/consistency cleanup.
- Practical scope: `gemini_gnirs_ifu` is listed as `Supported = False` in PypeIt's own spectrograph table (`doc/include/spectrographs_table.rst`); `gtc_maat` is listed `Supported = True`, but has no dev-suite `.pypeit` file or test data anywhere, and its dedicated doc page never mentions the IFU/MAAT mode. Both files carry other signs of in-progress support (`# HACK FOR HRIFU`, `# HACK FOR MAAT SIMS`, hard-coded `off1 = off2 = 0.`). The bug is only reachable via the opt-in `save_native=True` parameter for these two specific instruments.

**Fix implemented.** Given the above, this was treated as a real bug fix, not deferred:

- `gemini_gnirs.py`'s `GNIRSIFUSpectrograph.get_datacube_bins()` and `gtc_osiris.py`'s `GTCMAATSpectrograph.get_datacube_bins()` now return `(spec_bins, ybins, xbins)`, matching `keck_kcwi.py`'s already-correct order (previously both returned `(xbins, ybins, spec_bins)`).
- Removed the now-resolved TODO comment in `keck_kcwi.py`.
- Corrected the return-value docstring in all three concrete implementations plus the `Spectrograph` base class: the element order was stale (`(x,y,\lambda)`, matching the pre-`kcwi_dec_2024` convention) in the base class and both GNIRS/GTC-OSIRIS copies; `keck_kcwi.py`'s was already correct. Also fixed a separate, unrelated docstring bug present in all three concrete implementations (not `spectrograph.py`'s base version): the return-value block was mislabeled `Args:` instead of `Returns:`.
- Added `test_ifu_get_datacube_bins_wavelength_axis_first` to `pypeit/tests/test_spectrographs.py`, which calls `get_datacube_bins()` for `keck_kcwi`, `keck_kcrm`, `gemini_gnirs_ifu`, and `gtc_maat` with a `num_wave`/`slitlength` deliberately distinct from every spectrograph's fixed slice count, and asserts the returned bin-edge array sizes land in `(spec_bins, ybins, xbins)` order. Verified this test fails against the pre-fix code (confirming it actually catches the regression) and passes after the fix.

All tests in `pypeit/tests/test_spectrographs.py` and `pypeit/tests/test_datacube.py` pass (32 passed, 4 skipped due to `--remote-data=none`, unrelated to this change).

**Side note**: separately, the team lead set `supported = False` on `GTCMAATSpectrograph` (`gtc_maat`), which the spectrograph table previously listed as `Supported = True` despite the complete absence of dev-suite `.pypeit` files or test data for it (noted in the assessment above). As a matter of policy, an instrument should only be flagged `supported = True` once it has data that is consistently tested as part of the dev suite -- `gtc_maat` does not meet that bar today. (There may be other spectrographs in the codebase where this policy hasn't been consistently applied; this change addresses `gtc_maat` only.)
