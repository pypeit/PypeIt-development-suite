PypeIt bug report · pypeit/core/wavecal · holy-grail

Holy-grail dispersion truncation

patterns.quadrangles stores the dispersion and central wavelength of every 4-line pattern in unsigned-integer arrays, so 1.94 Å/px becomes 1 and anything below 1 Å/px becomes 0. Holy-grail then uses that truncated dispersion to report the fit rms in pixels and to convert the line-matching tolerance to ångström.

Fixing the dtype alone is not safe. On the data where this was found, the truncation is what makes holy-grail work: it lets 4-line patterns from the whole slit vote on the line IDs. With float dispersions, 13 of the 15 affected slits fall back to 3-line fits that are wrong by up to 29–112 Å towards the blue end, still passing the rms test, and one slit fails. The underlying problem is the line-ID vote in solve_slit, which only uses patterns within ±0.8 % of the peak dispersion, while the dispersion of these spectra changes by 7–8 % along the slit. A smaller fix (B, patch ready) corrects the reported rms and on this data changes no solution by more than 0.14 Å; it has been tested on one dataset only.

The defect and the fixes are generic. The evidence comes from Subaru/MOIRCS data; if you have not worked with MOIRCS, read Background first.

Found 2026-10-03 while adding Subaru/MOIRCS VB_K · PypeIt develop f3a1f1d27 · numpy 2.5.3

The defect

In quadrangles (and the unused curved_quadrangles) the output arrays for the pattern central wavelength and dispersion are created and appended with dtype=np.ulonglong. The dispersion tst is a float ratio, so it is truncated toward zero. The integer type is original: the 2018 numba version already declared these arrays nb.types.ulong (da90239b6, 2018-08-16). The numba removal (d92c50c8d, 2020-12-05) briefly made them float64, and 1fbb5e18b (2021-01-03, "Fixed a bug I introduced when I removed the numba dependency") restored the unsigned type, as the trailing comments show. So the truncation has very likely been there since 2018, apart from that month (the numba-era code was not run here). The uint64 index arrays on the neighbouring lines are fine.

  first fit it finds, replaces it only with a fit that has an rms below the

  on both halves of the spectrum are identified (autoid.py:2076–2093).

Background: the MOIRCS data

  
MOIRCS is the near-infrared imager and multi-object
  spectrograph of the Subaru Telescope (0.9–2.5 µm). The beam is split into
  two optically independent channels, each with its own camera, grism and
  2048×2048 Hawaii-2RG detector. PypeIt reduces the two as
  DET01 and DET02 of one exposure, with
  separate slit edges, tilts and wavelength solutions. Support is being added
  on the branch u/monodera/subaru_moircs_vbk (HK500 grism first,
  now VB_K).

  
The data. One multi-object mask
  (MO_CC0958PA200_1) observed with the VB_K
  grism, a K-band grism with about 1.94 Å per pixel. Each detector has 14
  science slits and 5 square boxes for alignment stars; the boxes are flagged
  BOXSLIT and skipped, which leaves the 28 science
  slits used here. The VB_K spectrum is longer than the detector, so
  every slit records a 0.39 µm window (2040 pixels × 1.94 Å) whose position
  depends on where the slit sits in the mask. Together the slits of this mask
  cover 1.90–2.54 µm.

  
Wavelength calibration from the sky. PypeIt has no
  usable lamp line list in the K band (its Th and Ar lists stop near 1.1 µm
  or are sparse), so the two 180 s science exposures, taken in an A–B
  dither, are typed arc,tilt,science and the night-sky OH
  emission lines are used (line list OH_MOSFIRE_K). OH lines are
  dense: holy-grail fits 46–60 lines per slit. The holy-grail run used
  fwhm = 6 px (measured 5.6–6.2 px), n_final = 4 and
  rms_thresh_frac_fwhm = 0.11, which gives per-slit rms
  thresholds of 0.60–0.68 px. The branch now uses reidentify
  with an archive built from these holy-grail solutions; everything in this
  report is from the earlier holy-grail run.

  
Why this data shows the bug. A dispersion of 1.94 Å/px
  sits between 1 and 2, so the truncation halves it (to 1) and the stored rms
  nearly doubles. The dense OH line list also gives the quadrangle search
  many patterns to match, so a quadrangle fit wins on about half of the
  slits. At dispersions below 1 Å/px the same bug has a different effect (the
  quadrangle pass is silently dropped) and the rms is not affected.

Evidence on real data

  
Subaru/MOIRCS, VB_K grism, mask MO_CC0958PA200_1: 28 slits on two
  detectors, wavelengths from OH sky lines (OH_MOSFIRE_K), true
  dispersion 1.93–1.96 Å/px. The calibrations are from one holy-grail
  pipeline run (run2; run3 reused them unchanged).
  Holy-grail solves all 28 without cross-matching. For 15 slits the
  winning pattern came from the quadrangle pass, bdisp is 0.9992,
  and the stored rms is 1.93–1.96 times the rms recomputed from the fit
  residuals and the solution's own dispersion. For the other 13 it came from
  triangles, bdisp is 1.91–1.97, and the stored rms is right.

  
  





  
Two fixes, tested

  
Both were applied at run time to an offline rerun of holy-grail on the
  same 28 sky spectra (holy_rms_check.py rerun); no PypeIt file was
  edited. The as-is rerun reproduces the pipeline's stored rms exactly. In
  that test fix B replaced bdisp on its way into
  fit_slit. The patch below makes the same change where
  bdisp is set, in HolyGrail.solve_patterns, because
  fit_slit is shared with reidentify,
  full_template and the echelle calibration, which the fix should
  not touch. Rerun with the patched package, all 28 slits give results
  identical to the tested fix B, and bdisp (and the "Patt match
  dispersion" log line) now reads 1.92–1.97 Å/px. A solution can be accepted
  with a single matched pattern line (patterns.py:800), hence the guard.

Three things point the same way. (1) The current solutions agree with
  each other everywhere (cc 0.945–0.994 at zero shift), and every solution
  that fix A changes correlates worse than the one it replaces. The reference
  is built from the current solutions of the other slits, but 13 of them come
  from triangle patterns that neither fix changes, so it is not simply
  circular. (2) Without reference to other slits, the fix-A fits of the
  changed slits keep fewer OH lines (36–51 against 46–60) and their true rms
  is 1.6–4.3 times higher (0.22–0.57 px against 0.075–0.19 px). (3) On DET01
  the current solutions follow a linear relation between the wavelength at
  the middle pixel and the slit position in the mask image, with residuals
  ≤ 10 Å; the fix-A solutions were not run through this check. The fix-A
  fits still reach rms 0.22–0.57 px, under the per-slit thresholds of
  0.60–0.68 px, so holy-grail would accept them. The next section shows why
  they are wrong.






  
Why the dtype fix makes it worse

  
Two further experiments, run the same way, explain the result: holy-grail
  with triangles only (holy_rms_check.py variant T, which runs
  run_brute_loop with rng_poly = [3]), and a look at
  where along the slit each solution goes wrong
  (holy_rms_where.py).

  
Without quadrangles, the same slits fail

  
With triangles only, the 13 slits won by triangle fits are unchanged and
  all 15 others are lost: 14 are off by 29–191 Å and DET02 909 finds no
  solution. Fix A gives exactly the triangles-only result on 14 of these 15
  (the same max |Δλ| to 0.01 Å; 909 fails in both); only DET01 337 is still
  won by a correct quadrangle fit. So with float dispersions the quadrangle
  pass does not produce wrong fits of its own: it no longer replaces the wrong
  triangle fits. On this data the quadrangle pass is needed, but only in its
  truncated form.

  
The pattern search finds the right answer; the vote uses only part of it

  
The histogram peak is at the stored solution: for all three slits probed
  with triangles, and with float quadrangles for two of them (on DET01 469
  it is 4 % low). The votes in the window around the peak match the votes
  around the stored solution.

  

  
The problem is the next step. solve_slit lets only the
  pattern solutions within ±3 log-dispersion bins (nseld = 3,
  ±0.81 %) of the peak vote on the line IDs (nseld in the signature at autoid.py:2752, used at 2852–2870). The
  dispersion of every VB_K slit changes by 7.1–8.3 % along the slit, mostly
  towards the blue end, so only patterns from the part of the slit where the
  local dispersion is close to the peak value take part. For DET01 slit 1855
  the 25 lines identified by triangles are all correct, but they lie at
  pixels 1240–1987; the fit is right there and drifts to −111 Å at pixel 0.
  The truncated quadrangles put every dispersion between 1 and 2 Å/px into
  one bin, so patterns from the whole slit vote: 43 correct IDs over pixels
  1–1987, and the fit is right everywhere.

  
  
  
Widening the window helps, but is not enough

  
With triangles only and the window widened to ±15 bins (±4 %), DET01 1855
  and 469 become correct everywhere (51 and 29 identified lines; three wrong
  IDs on 469 are rejected by the fit). DET02 1665 improves but is still −37 Å
  at pixel 0, with six wrong IDs at the blue end. So the narrow vote window
  is the cause, and a wider window alone is only a partial remedy.






  
Who is affected

  
    
    
  • Every holy-grail user. holy-grail is the
    default method of WavelengthSolutionPar, and 14
    spectrograph files in develop also set it explicitly, some only
    for particular setups or as a fallback: . (The
    new subaru_moircs on this branch uses it for grisms without an
    archive.)
    • 
    
  • Below 1 Å/px (many optical gratings): the quadrangle
    pass has very likely never returned a usable pattern (apart from one
    month in 2020–21), so these setups have been solved by triangles alone. Their dispersion estimates and rms are not
    affected, but fix A would switch the quadrangle search back on for all of
    them.
    • 
    
  • 1 Å/px and above (low-resolution and near-IR modes):
    when a quadrangle pattern wins, the stored rms is too large by
    dispersion / floor(dispersion), up to 2×. The inflated value is also what
    rms_thresh_frac_fwhm is compared with, so good solutions can be
    rejected and sent to cross-matching, and the line-matching tolerance is
    tighter than match_toler says.
    • 
    
  • Spectra whose dispersion varies along the detector
    by more than about ±0.8 % around its central value: the line-ID vote uses
    only part of the spectrum, and the fit can drift outside that part
    (see Why the dtype fix makes it worse). On VB_K this is
    hidden wherever a truncated quadrangle fit wins. How common such setups
    are, and whether their holy-grail solutions suffer, was not checked.
    • 
    
  • Only MOIRCS VB_K was measured. Other instruments were not tested
    here.
    • 
  






  
Suggested next steps

  
    
    
  1. Prefer fix B, and run it through the development suite's
    holy-grail setups before merging. It fixes the reported rms, the
    rms_thresh test and the matching tolerance, and on this data
    changes no solution by more than 0.14 Å, but only 15 affected slits from
    one instrument were tested. Wherever a quadrangle pattern wins, it makes
    holy-grail more permissive: the rms roughly halves and the matching
    tolerance roughly doubles, back to what match_toler says. Fits
    that are now rejected or sent to cross-matching may then be accepted, and
    more lines get matched, which could admit wrong lines on sparse or
    blended spectra. Where triangle patterns win (expected for most setups
    below 1 Å/px), the estimate it replaces is already close, so the change
    should be negligible; that is expected, not measured. Computing the
    dispersion from the fit inside iterative_fitting is an
    alternative (not tested here); it would also change the rms reported by
    reidentify (autoid.py:1325) and pypeit_identify
    (gui/identify.py:704 and 1352). A patch is ready:
    pypeitdev/subaru_moircs_vbk/patches/holygrail_bdisp_from_matched_lines.patch,
    with a new unit test, pypeit/tests/test_holygrail_dispersion.py,
    that fails on the current code.
    2. 
    
  2. Recheck parameters tuned under the bug. Any
    rms_thresh_frac_fwhm or match_toler value chosen
    while looking at the inflated rms may be stricter than intended once the
    rms is right. This includes the MOIRCS VB_K tuning that led to this
    report.
    3. 
    
  3. Do not apply fix A on its own. It removes the
    accidental widening of the vote: on this data 13 of the 15 affected
    slits fall back to wrong triangle fits and one fails.
    4. 
    
  4. Fix the line-ID vote for dispersions that vary along the
    detector. Options, of which only the first was tried: widen the
    dispersion window (nseld; fixes 2 of 3 test slits here); vote
    with a looser dispersion constraint, which is what the truncation does by
    accident; or refit with the identified lines and re-identify across the
    whole spectrum before the final fit. Any of these needs the development
    suite. Only after this is fix A safe, and only then is it worth deciding
    whether the quadrangle search is needed at all: below 1 Å/px it has very
    likely contributed nothing since 2018, and on VB_K its value comes from
    the truncation, not from the 4-line design.
    5. 
    
  5. Add unit tests: quadrangles returns float
    dispersions equal to the input (the reproduction above), and the rms
    returned by iterative_fitting does not depend on the
    dispersion estimate passed in.
    6. 
    
  6. Fix or remove curved_quadrangles, which has the same dtype
    and no callers.
    7.
