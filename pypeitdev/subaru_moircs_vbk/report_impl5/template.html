VB_K wavelength archive

VB_K now uses reidentify with a 28-slit OH archive. On the test mask it solves every science slit with the same solution as holy-grail. Leave-one-out and cross-detector tests found one slit that the default line-matching tolerance gets wrong, so VB_K sets match_toler = 0.75.

Implementation #5 · 2026-10-03 · baseline run3 (holy-grail) · rerun run5 (reidentify)

The archive

All 28 holy-grail solutions from run3 pass the HK500 selection (rms < 0.5 px, at least 40 lines, monotonic) and go into reid_arxiv/subaru_moircs_VB_K.fits, 14 per chip. VB_K disperses past the detector edges, so each slit sees a 0.39 µm window set by its position in the mask. Together they cover 1.90–2.54 µm. No slit in this mask reaches 1.8 µm, and OH lines stop at 2.499 µm, so the reddest ~250 px are extrapolated.

Pipeline rerun

run5 is a full reduction from scratch with the new defaults. It solves the same slits as holy-grail, and every solution agrees with run3 to 0.12 Å or better (median ≤ 0.05 Å) over the fitted range. The extracted science and standard spectra are unchanged: same objects, same S/N, wavelengths within 0.054 Å. The rms below is recomputed from the fit residuals and each solution's own dispersion; see the last section for why holy-grail's stored value is not used.

Robustness tests

run5 reidentifies each slit against its own spectrum, which is trivially right. To see how the archive behaves on a new mask, each run3 sky spectrum was also solved against an archive without that slit (leave-one-out) and against an archive made from the other chip only (cross-detector). A slit passes when rms < 0.5 px, at least 30 lines are fitted, and the solution stays within 2 Å (~1 px) of holy-grail everywhere in the fitted range.

Other settings were tried on the failing slit and did not help: nreid_min 2–4 (3–4 also lose slits at the ends of the coverage), cc_thresh 0.8–0.88 (still 23 Å off), cc_local_thresh, nlocal_cc, a linear stretch, n_final 3 or 5, sigdetect 3 or 10, reid_cont_sub, and cc_percent_ceil.

The failing slit: DET01 slit 758

With the default tolerance the leave-one-out solution of slit 758 has rms 0.36 px, which passes PypeIt's rms test, but it is off by 12–37 Å beyond pixel ~1700, where two different lines were both identified as 23713 Å. The cause is the cross-correlation step: each archive spectrum overlaps the slit only in part (shifts up to ~1100 px), and the fitted stretches come out at 0.97–1.05, while the real dispersions differ by only ±1% (1.928–1.963 Å/px). The stretch limits are fixed in PypeIt's core code (wvutils.xcorr_shift_stretch), so they cannot be set from the spectrograph file. A tighter match_toler keeps the iterative fit from absorbing the misidentified lines.

Holy-grail's stored rms is too large for some slits

For 15 of the 28 run3 slits, the stored "rms in pixels" equals the rms in ångström, about twice the true value. Holy-grail divides by its own rough dispersion estimate, which came out at 0.999 Å/px for these slits instead of ~1.94 Å/px, because patterns.quadrangles stores pattern dispersions as unsigned integers. The solutions are correct; the reported rms, the rms_thresh_frac_fwhm test and the line-matching tolerance are affected. The fix belongs in PypeIt's core code, outside this project's files; it is written up for the team in a separate bug report.

Caveats

  • Self-referential. The archive comes from the same mask it is tested on. The leave-one-out and cross-detector tests are the best check possible here; a second VB_K mask, with other slit positions and another night, is still needed.
  • What to watch on a new mask: a red or blue end that is wrong while the rms looks normal. Holy-grail solved all 28 slits of this mask and is the fallback.
  • Coverage: 1.90–2.54 µm. Slits that reach below 1.90 µm on another mask have no archive match there.
  • HK500 also uses reidentify with the default tolerance. It was not changed (the HK500 data are not on this machine), but the same failure could occur.
  • Speed: each slit is cross-correlated with all 28 archive spectra, about 5–6 minutes per chip.
