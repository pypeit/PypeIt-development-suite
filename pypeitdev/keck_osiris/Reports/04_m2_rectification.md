## 3. Design of the core module

### 3.1 Orientation

Both solvers work on the **raw** frame: `image[row, column]` exactly as
stored in the FITS file (rows = cross-dispersion, columns =
dispersion, wavelength *decreasing* with column).  They return
`(ncol, nslice) = (2048, 1216)` arrays: axis 0 is the **raw detector
column, not flipped**, axis 1 the slice index.  This is already PypeIt's
`(spec, spat)` layout, but with the spectral axis reversed.  Because the
spectrograph has `specflip = True` and the M3 `rectify` step runs after
`orient`, M3 must either (a) un-orient the processed image (transpose
and flip back to the raw layout), call the solver, and flip axis 0 of the
output, or (b) transpose and flip the matrix.  Option (a) is two array
views and keeps the matrix untouched; I recommend it.

### 3.2 `rectify_drp`

All 2048 columns are solved at once.  The forward model is a sparse
`(2049, 1216*16)` scatter operator applied to `B * c`; the residual is
gathered back with the `(1216, 16)` row index.  The schedule is that of
`spatrectif_000.c`: sharpened kernel `B^3/sum B^3` accumulated and
applied with the `+0.4` (iterations 0-9) / `-0.2` (10-14) coupling to
slices +/-64, plain back-projection with `B/sum B` from iteration 15,
5-tap `[0.1, 0.2, 0.4, 0.2, 0.1]` smoothing of columns 2-2045 after
iterations 12-17, division by 1.28.  Noise: `sigma_out = sum_l fblame *
sigma` on good pixels (the DRP rule; not divided by 1.28); mask: good
if more than half (4.5/9) of the `fblame` weight is on good pixels.

Found while porting: the C code tests `Quality[jj][i]` (detector rows
0-15) instead of `Quality[j][i]` when it builds the output mask and noise
(an indexing slip).  The port uses the intended rows; the vet test
reproduces the slip only to emulate the DRP (`drp_c_quality_bpm`).

### 3.3 `rectify_lstsq`

The prompt asked for 64 independent bands of <= 19 unknowns.  The data
show that the bands are **not** independent: at a central column every
one of the ~1017 active slices overlaps its neighbours and the slice
profiles chain through all 2048 rows (no empty row separates the bands;
242 slice footprints straddle a 32-row boundary).  Solving the bands
independently (`couple_bands=False`, kept for diagnostics) agrees to
0.04 % in the median but is wrong by up to a factor of 5 at band edges.

What does hold is that a slice (`band = s % 64`, the lenslet row) only
overlaps slices of the same or the two adjacent bands (checked at run
time).  The normal matrix `A^T W A` of each column is therefore block
tridiagonal with 64 blocks of 19 x 19, and is solved exactly with a
batched block-Thomas algorithm over all columns (256 at a time).  The
variance is `diag((A^T W A)^-1)`, from the forward and backward Schur
complements.  Unknowns with no weight (dark slices, fully masked
windows) get an identity row and `ivar = 0`.  The solution is divided
by 1.28 (and `ivar` multiplied by 1.28^2) to stay on the DRP scale; the
mask uses the DRP rule.  The synthetic test checks that the predicted
variance matches the scatter of 100 noisy realisations (ratio 0.99).

### 3.4 Narrowband split and DRP grid

`narrowband_split` follows `assembcube_000.pro`: broadband filters map
slice `sp` to `(sp % 64, sp // 64)` of a 64 x 19 cube (coefficients at
`(row+1, col+16)`); narrowband filters use slices 0-1023 only, each
holding three lenslets head to tail at `(sp%64+2, sp//64+3)`,
`(sp%64+1, sp//64+19)`, `(sp%64, sp//64+35)`, plus
`(min(sp%64+3, 65), sp//64-13)` for `sp > 831` (66 x 51 cube; the
clipping at row 65 makes three extras overwrite each other, as in the
DRP).  `resample_to_drp_grid` reproduces `assembcube`: IDL-style linear
interpolation with extrapolation over good pixels, the "complete"
lenslet rule, quality interpolation, and the Keck I row flip.

## 4. Verification

### 4.1 DRP provenance of the reference cube

To compare like with like I traced how the reference cube was made (its
header carries the DRF): Subtract Frame (011), Adjust Channel Levels,
Remove Crosstalk, Glitch Identification, Clean Cosmic Rays, Extract
Spectra (40 iterations, ARP_SPEC), Assemble Data Cube, Correct
Dispersion; produced from a September-2016 download with the DRP of
that time.  For H2RG data:

- Adjust Channel Levels subtracts the per-column median of rows
  2032-2044 (reproduced, `subtract_reference_rows`).
- Crosstalk and glitch removal are skipped.
- **Clean Cosmic Rays was active in 2016** (it has been skipped for the
  H2RG since OsirisDRP commit 8d331a2, 2017-09-07).  The vet test ports
  the 2016 version (commit 9f11afd: strips of 100 pixels along each
  row, two passes, 13 295 pixels flagged here).
- `DTMP7` is missing from the truncated header of frame 010; the DRP
  reads it as 0 K and *extrapolates* the CTE table, giving
  `frac_expan = 0.99978` (a ~1.5 px wavelength shift).  This is
  reproduced by `drp_grating_expansion(None)`.
- The reference used `osiris_wave_coeffs.fits`, which in 2016 was the
  2016 solution; today that file holds the 2021 solution.  The M1
  epoch selection (`osiris_wave_coeffs_160101_170508.fits`) is the right
  one: with it the cube is reproduced to 1e-5.
- Correct Dispersion shifts each wavelength plane bilinearly by the
  atmospheric refraction (up to 0.028 lenslet here; planes below 0.01
  lenslet are skipped); reproduced by `drp_correct_dispersion`.  Without
  it the quasar spaxel is 1.5 % high at the red end.
- `DQ` is 9 everywhere and the Keck hot/dead masks were not applied by
  the DRP.

### 4.4 What limits the agreement with PypeIt input

With the DRP-emulated input the agreement is at the 1e-5 level, so the
0.7 % median with PypeIt input is entirely due to input differences,
almost all **cosmic rays**: the 2016 DRP flagged 13 295 pixels that
PypeIt's input does not mask.  A single hit changes a faint spaxel by
5-20 % (`m2_per_lenslet.png`, S/N 20-60), hence the 6 % 90th percentile.

## 5. Deviations and findings

1. **Weighted `lstsq` and the quasar (2 %).**  With the PypeIt
   (Poisson + read noise) weights the quasar spaxel is 2.1 % low (6 % at
   the red end); unweighted (`ivar=None`) it is +0.02 %, like the DRP
   (which is effectively unweighted).  The reason is PSF-model error, not
   noise: at the quasar the best fit leaves residuals of up to ~40 sigma
   (5-25 % of the pixel value, e.g. 1271 ADU observed vs 324 modelled two
   rows from the peak), so down-weighting the bright core moves flux.
   Within the 5 % tolerance, but see Q&A 1.
2. **Band coupling** (section 3.3): exact block-tridiagonal solve rather
   than independent bands.  Same cost (2.3 s).
3. **C mask/noise indexing slip** (section 3.2): not reproduced in the
   port (only in the vet-test emulation).
4. **DRP noise rule**: `sigma_out = sum fblame * sigma` is a linear sum
   (fully correlated noise) and is not divided by 1.28; it comes out at
   0.53 times the `lstsq` sigma for the same input.  Kept as specified
   for fidelity; see Q&A 3.
5. **Output orientation** (section 3.1): `(2048, nslice)` in the raw
   column order; M3 must flip.
6. **DRP preprocessing to be carried into PypeIt**: the reference-row
   column correction (now `subtract_reference_rows`, on by default in
   the script) and some cosmic-ray handling (Q&A 2).  The `DTMP7 = 0 K`
   extrapolation is a DRP bug reproduced only for the comparison; M1's
   `grating_expansion(None) = 1` stays (Q&A 4).
7. `pypeit_osiris_rectify` imports at the top of the file (per the
   coding rules), which makes `-h` a little slower than other scripts.
8. The `lstsq` solution and ivar are scaled by 1.28 like the DRP, so both
   solvers share one flux scale; it cancels in flux calibration.
